## 1. 총평

**통과선 대비 위치: 상위. 단 통과는 아니다.**

이 저장소의 데이터 층은 표본보다 앞선 자리가 여럿이다 — 복원 드릴이 링크가 아니라 **체인**을
흘리고(Litestream 문서는 복원 훈련을 의무로 두지도 않는다), 서명키 분실 절차가 적혀 있고(Tauri v2
문서엔 그 절이 없다), 마이그레이션 체크섬 방어가 3겹이고, 툼스톤 GC 부재가 *"안 만든 것이 아니라
만들지 않기로 한 것"* 으로 착수 조건까지 기록돼 있다. 신뢰 경계 19개 입구를 전수로 짚었을 때
**런타임 검증이 빠진 곳은 사실상 0**이었고, 경로 탈출·커맨드 인젝션·SSRF 는 각각 테스트로 잠겨 있다.

그럼에도 통과가 아닌 이유는 **결함 19건이 세 개의 뿌리에서 반복해서 나오기** 때문이다. 셋 다
「이 저장소가 이미 아는 것」의 **적용 범위가 하나씩 모자란** 형태다: 버전 스큐를 알면서 테이블
축만 덮었고, 「손으로 적은 목록은 표류한다」를 문서에만 적용하고 **코드 안의 목록**에는 적용하지
않았고, 내구성 관용구를 세 종료 경로 중 둘에만 붙였다. 즉 이 회차의 발견은 «몰랐던 것»이 아니라
**«알던 것의 가장자리»** 이고, 그래서 처방이 전부 싸다(19건 중 비용 S 가 14건).

**범위와 그 밖.** 데이터 축만 팠다. 성능(부팅 전량 읽기·flush O(전체행))·코드 구조(파일 크기)·
ux(설치 중 busy 미해제)는 각각 수치를 확보했으나 **판정하지 않았고** §8 로 이월했다.

## 3. 지적 — 심각도순

증거등급 · 비용(S/M/L) · 폭발 반경 병기. **전 건 메인이 파일을 직접 열어 재확인**했다(`검증기록.md`).

### Major

**D001 · `web/src/lib/db/sqlite.worker.ts:77-91` · [읽음] · S**
폰 마이그레이션이 **비원자**다 — `d.exec({sql: m.sql})` 와 `INSERT INTO _migrations` 가 별개
문장이고 감싸는 트랜잭션이 없다. **정작 20줄 아래 `batch` 핸들러(:112-123)는 BEGIN/COMMIT/ROLLBACK 을
쓰면서 «워커는 단일 커넥션이라 sqlx 풀의 BEGIN 잠금 함정이 없다»고 주석으로 근거까지 적어 뒀다.**
같은 파일이 덜 중요한 쓰기에는 원자성을 주고 스키마 이행에는 안 준다.
*실패*: 폰 새 설치가 v1~v11 을 순차 실행하는 중 iOS Safari 가 백그라운드 탭을 죽인다. `009`
(`CREATE TABLE summaries_v9` → `INSERT…SELECT` → `DROP TABLE summaries`)가 `_migrations` 기록
전에 끊긴다 → 다음 실행이 009 를 재실행 → `table summaries_v9 already exists` → `open()` throw →
`killWorker` → null. `isSqlitePrimary()` 는 폰에서 여전히 true 라 `runWrite` 가 매번 `unavailable`.
**그 브라우저에서 폰의 로컬 저장이 영구 불능이고 OPFS 를 지울 방법이 사용자에게 없다.** 전
마이그레이션이 `CREATE TABLE`(`IF NOT EXISTS` 아님)이라 009 만의 문제가 아니다.
*수정*: `migrate()` 루프 안을 `BEGIN`/`COMMIT`/`ROLLBACK` 으로 감싼다(바로 아래 `batch` 와 동일 관용구).
*폭발 반경*: 폰 1대의 로컬 저장 전량 · **사용자가 되돌릴 수 없다**(정본은 D1 에 남는다).

**D002 · `web/src/lib/cloud/schema.ts:231-241` · [읽음] · S**
수신 관용(H16)이 **테이블 축에만** 있고 **열 개수 축에는 없다**. `known()` 은 `tbl` 만 보고,
살아남은 행은 `OutboxBatchSchema` 의 길이 검사(:86-94)에 걸려 **배치 전체가 거부**된다.
*실패*(가설 아님 — 같은 형태가 이미 지나갔다): `009` 가 `summaries` 를 `['sid','ord','value']`에서
`['sid','id','ord','value']`로 바꿨다. 009 가 지시하는 배포 순서는 «D1 먼저, 앱 나중»이고 폰 SW 는
autoUpdate·데스크톱 업데이터는 **수동 승인**이다. 그 창에서 구버전 데스크톱이 pull 하면 `tbl` 은
알려진 이름이라 관용 필터를 통과한 뒤 길이 불일치로 **배치 전량 거부** → `commitPullMark` 미도달 →
**그 기기의 수신이 영구 정지**. 화면은 `failed` 토스트 한 줄이고 «다음 시도에 다시»라고 말한다(거짓).
*수정*: `known` 을 `knownRow`/`knownTomb` 으로 갈라 `key.length`·`data.length` 를 필터 단계에서
본다(`upto` 는 종전대로 전진 — H16 이 그 근거를 이미 소유한다).
*폭발 반경*: 업데이트 안 한 기기 전부의 **수신 영구 정지**(유실 아님 · 수렴 정지) · 앱 업데이트로만 복구.

**D003 · `web/src/lib/db/boot.ts:152-173` · [읽음] · M**
localStorage→SQLite **1회 이관에 완료 마커가 없다.** 「이관됐는가」의 유일한 판정은 `readRows()` 가
non-null 인가이고, 그 함수는 **`settings` 또는 `meta` 에 한 행이라도 있으면** non-null 을 준다
(`sqlite.ts:279`). `_migrated` 는 모듈 지역 변수라 재부팅에 사라진다. **부분 이관과 완료 이관을
구분할 수 없다.**
*실패*: 데스크톱 `writeRows` 는 `db.batch` 가 없어 **순차 `execute` 폴백**이고(`sqlite.ts:395` —
그 사실을 워커 주석이 «데스크톱은 풀 제약상 순차 비원자»로 확인해 준다) 문장 순서는 `TABLES` 순이다.
`meta`·`settings` 를 쓴 직후 프로세스가 죽으면 예외가 없으므로 `ok:false` 경로도 안 탄다. **다음
부팅**은 `settings` 행을 보고 non-null → DB 가 정본으로 확정 → `cbms`·`backlog`·`tasks`·`events`·
`summaries` 가 사라진다. localStorage 에 원본이 그대로 있지만 **그것을 읽는 코드 경로가 더 이상 없다.**
*수정*: 마커를 `sync_state` 에 둔다(`meta` 는 `rows.ts` 매퍼 소유라 다음 flush 의 `diffRemovals` 가
지운다 — `sync_state` 가 별도 표인 이유가 이것이다). `started` 를 이관 **전에** 쓰고 성공 후 지운다.
재개 시 부분 DB 를 기준선으로 세우면 diff 가 나머지만 채우므로 멱등. 기존 설치는 마커가 없어 거동 변화 0.
*폭발 반경*: 그 기기의 활동 데이터 전량이 화면에서 소실(물리적으로는 회수 가능하나 UI 경로 없음).

업데이트 설치가 **저장 확정 없이 프로세스를 갈아탄다.** 창 닫기·트레이 종료는 `StorageGuard.tsx:26-42`

처방은 벤더 동작과 무관하게 안전하다(가드가 뛰든 안 뛰든 확정을 먼저 하는 것이 옳다).
*수정*: `setBusy(true)` 직후 `StorageGuard` 와 **같은 4줄**을 넣는다.
*폭발 반경*: 마지막 400ms~30초의 편집 1건 · **되돌릴 수 없다**(pre-image 도 안 쌓였다).

**D005 · `web/src/lib/db/docs.ts:53` (+ `cloud/contract.ts:85`) · [측정] · M**
실 DB `docs` 표에 **3행 51,793 B** 가 있다 — `lh:reads`(103 B) · `artifact:reads`(**40,834 B**) ·
`artifact:markets`(10,856 B). 셋 다 P10 W4(2026-08-07)에서 화면이 `survey/` 로 가며 은퇴한 세입자다.
지금 이 셋은:
- **읽을 수 없다** — `DOC_KEYS = ['ics:feed']` 뿐이라 `isDocKey` 가 false → `docGet` 이 localStorage 로 흐른다.
- **지울 수 없다** — 전 저장소에 `DELETE FROM docs` **0건**(메인 재확인)이고, `docs` 는 `rows.ts` 의
  `TABLES` 밖이라 `diffRows` 가 DELETE 도 툼스톤도 만들지 못한다. **앱의 어떤 경로로도 도달 불가.**
- **그런데 나른다** — `OUTBOX_TABLES` 에 `DOCS_SPEC` 으로 들어 있고, 실측 `watermark = 1787242608409`
  가 세 행의 `updated_at`(최대 1785602138061)보다 **크다 → 이미 D1 에 밀려 있다.** pull 이 폰 OPFS 로
  같은 51KB 를 내린다.
- **매 부팅에 메모리로 올린다** — `initDocs()` 의 `SELECT key, value FROM docs` 가 셋을 `_cache` 에 담는다.
`docs.ts` 머리주석은 *"빈 채로 두되 빈 것을 명시한다"* 고 적었지만 **표는 비어 있지 않았다.**
*수정*: **순서가 처방의 일부다.** ① `backupPayload` 에 `docs` 를 싣는다(회수) ② `docDelete` 를
만들되 **툼스톤을 먼저** 낸다(`contract.ts:94` 가 이미 그 규칙을 못박아 뒀다) ③ `initDocs` 가
미지 키를 **지우지 않고 보고**한다(설정 › 진단). ①을 건너뛰고 ②만 하면 `lh:reads`(사용자 저작물)가
회수 불가 상태로 사라진다.
*폭발 반경*: 로컬 51KB + D1 51KB + 폰 51KB · 영구.

### ① 여러 버전의 클라이언트가 동시에 존재한다 — **그 사실을 프로토콜이 모른다**
