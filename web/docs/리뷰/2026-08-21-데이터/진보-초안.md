## 행 1 — 스키마 버전 핸드셰이크 (ⓓ = **없음**) ⭐ 이 절의 본체

- **메커니즘**: 클라이언트가 접속할 때 **자기가 빌드된 스키마를 서버에 보낸다.** 서버가 자기 것과
  호환되지 않으면 **연결을 거부**하고 클라이언트는 `onUpdateNeeded(reason.type ===
  'SchemaVersionNotSupported')` 를 받는다. (Zero — *"When a client connects to `zero-cache`,
  it sends the schema it was built against."*)
- **ⓐ 왜 의무인가**: 로컬 우선 앱에서 클라이언트 배포는 **동시에 일어나지 않는다.** 기기 A 는 오늘
  자동 업데이트를 받고 기기 B 는 3주 뒤에 앱을 연다. 그 창 동안 두 코드가 같은 서버 데이터를 읽고
  쓴다. 핸드셰이크가 없으면 그 창은 **관측되지 않는다** — 아무도 실패하지 않고, 조용히 갈린다.
- **ⓑ 없으면 나는 사고**: 구버전이 신버전 레코드를 pull → 모르는 필드를 떨군 채 로컬에 저장 →
  그 로컬을 다음에 push → **신버전이 쓴 데이터가 지워진다.** 사용자에겐 «갑자기 사라졌다» 로 보이고
  두 기기 모두 «내 쪽은 정상» 이다.
  ⚠ 우리에겐 완화 장치가 하나 있다 — `AppStateSchema` 가 **`.passthrough()`** 다
  (`cloudflare-런북.md:313` 이 *"I1(백업 호환)용 **의도**"* 라 적었다). 즉 모르는 필드가 통과한다.
  **그러나 그건 zod 계층의 성질이지 계약이 아니다** — 그 한 글자를 `.strict()` 로 바꾸는 순간
  위 사고가 열리고, **막는 검사가 없다.** 실제로 같은 줄이 *"신뢰 경계에선 정반대로 작동한다"* 고
  적어 이 앱에 `.strict()` 를 원하는 힘이 존재함을 스스로 증언한다.
- **ⓒ 대가**: 서버가 구버전 클라이언트를 **막는다** — 앱을 못 쓰게 되는 사용자가 생긴다. Zero 는
  그래서 창을 명시로 좁힌다: *서버는 같은 메이저 + **한 메이저 뒤**까지만*. 즉 "영원한 호환"을
  포기하고 **호환 구간을 유한하게 선언**하는 것이 그 대가다.
- **ⓓ 우리 현재**: **없음.** `[측정]` `server/src/index.ts` · `web/src/lib/cloud/contract.ts` ·
  `web/src/lib/cloud/schema.ts` 에서 문자열 `version` 이 **0회**. `onUpdateNeeded|schemaVersion|
  SCHEMA_VERSION|appVersion` 도 `cloud/*.ts` + `server/src/*.ts` 전체에서 **0회**.
  즉 프로토콜에 **버전 필드 자체가 없다.**
- **ⓔ 우리 규모의 최소형**: **서버가 막게 하지 마라** — 1인 앱이 자기를 잠그는 것이 더 나쁘다.
  대신 ① push 요청에 헤더 `x-hub-schema: <로컬 최대 마이그레이션 버전>` 한 줄 ② 서버가 자기
  `_sqlx_migrations` 최대값과 비교해 **응답 바디에 `serverSchema` 를 담아 돌려준다**(막지 않는다)
  ③ 클라이언트는 `serverSchema > 내 것` 이면 **push 를 보류하고 배너 하나**("이 기기가 낡았습니다").
  헤더 1줄 + 비교 1줄 + 배너 1개. **그리고 `.passthrough()` 를 「의도」에서 「검사」로 승격**하라 —
  `contract.test.ts` 에 *"모르는 필드가 왕복에서 보존된다"* 단언 하나. 지금은 주석이 지키고 있다.

## 행 2 — Expand / Migrate / Contract 순서 규약 (ⓓ = **없음**)

- **메커니즘**: 스키마 변경을 **세 배포로 쪼갠다.** 확장(추가)은 *제공자 먼저* — DB → API →
  클라이언트. 축소(제거)는 **정확히 반대로** *소비자 먼저* — 클라이언트 → API → DB. 그리고
  **엔진 버전 변경과 스키마 변경을 같은 PR·같은 배포에 섞지 말라**고 명시한다. (Zero)
- **ⓐ 왜 의무인가**: 순서가 종류마다 **반대**이기 때문이다. 한 배포에 섞으면 그 배포는
  「추가 순서」와 「제거 순서」를 동시에 만족해야 하는데 **그런 순서는 존재하지 않는다.**
- **ⓑ 없으면 나는 사고**: 컬럼을 지우는 마이그레이션을 앱 배포와 함께 내보내면, 아직 구버전을
  쓰는 기기의 쓰기가 전부 실패하거나(운 좋으면) 조용히 삼켜진다(운 나쁘면). 우리 구조에선 더
  나쁘다 — **D1 과 로컬 SQLite 가 같은 폴더를 공유하는데 적용 시점이 다르다.** `wrangler d1
  migrations apply` 는 배포자가 손으로 치고, 로컬은 **앱을 여는 순간** 적용된다. 두 시계가 다르다.
- **ⓒ 대가**: **배포가 3배로 늘고 «중간 상태»를 견디는 코드를 일부러 남겨야 한다** — 한동안 죽은
  컬럼과 산 컬럼이 공존한다. 즉 **잔재를 자발적으로 감수하는 거래**다(§잔재와 정면으로 충돌하는
  의무이고, 그래서 «언제까지» 를 함께 적는 것이 그 규약의 나머지 절반이다).
- **ⓓ 우리 현재**: **없음.** `[측정]` 마이그레이션 11개는 **전부 확장 전용**(`DROP COLUMN` 0회).
  즉 지금까지 이 문제가 안 난 것은 «규율이 있어서» 가 아니라 **«아직 아무것도 안 지웠기 때문»** 이다.
  `src-tauri/migrations/README.md` 는 *"기존 파일을 고치지 마라"*(sqlx 체크섬)를 매우 강하게 적지만
  **«언제 무엇을 지워도 되는가»는 한 줄도 없다** — `DROP COLUMN|축소|제거하려면|deprecat` 로
  README + 클라우드전환-설계 전문을 훑어 해당 규약 0건. 첫 축소 마이그레이션이 그 공백을 만난다.
- **ⓔ 최소형**: 기계 0. `migrations/README.md` 에 **세 줄** — *"추가는 DB→앱. **제거는 앱→DB**.
  제거 마이그레이션은 앱이 그 컬럼을 안 쓴 채 **최소 한 릴리스가 배포된 뒤에만.**"* 이 저장소의
  문제는 집행자 부재가 아니라 **그 문장이 존재하지 않는 것**이다(README 가 이미 읽히는 문서다).

## 행 3 — 유실 창을 **수치로** 선언하기 (ⓓ = **부분**)

- **메커니즘**: Litestream 은 *"asynchronous replication, creating a data loss window of
  approximately **one second** by default"* 라고 **기본 유실 창을 수치로 적는다.** 문서는 정기
  복원 테스트를 요구하지 **않는다** — 요구하는 것은 «얼마나 잃을 수 있는지 알고 있을 것» 이다.
- **ⓐ 왜 의무인가**: 백업의 값은 «있다» 가 아니라 **«마지막 백업 이후 무엇을 잃나»** 다. 그 수를
  모르면 백업 주기를 정할 근거가 없고, 주기 없는 백업은 기분에 달린다.
- **ⓑ 없으면 나는 사고**: 사용자가 «백업했다» 고 안심한 상태에서 그 사이 3주치 학습 기록이
  로컬에만 있다. 디스크가 죽으면 그 3주는 **백업이 있었기 때문에 더 놀랍다.**
- **ⓒ 대가**: 수를 적으면 **그 수를 지켜야 한다** — «1초» 를 적은 순간 그것이 계약이 되고,
  못 지키면 문서가 거짓말이 된다. 그래서 대개 안 적는다.
- **ⓓ 우리 현재**: **부분.** `Settings.tsx:409` 가 `볼트 백업: N일 전` 을 말하고 `:783` 이
  «브라우저 캐시를 지우면 데이터가 사라질 수 있다» 고 경고한다 — **경과 시간은 있다.**
  없는 것은 **그 N일에 무엇이 들었는지**다(챕터 몇 개·시간 몇 h·복습 몇 건).
- **ⓔ 최소형**: 그 배너 문구 하나. `백업이 12일 지났어요` → **`백업 이후 새 기록 37건(투입 14h)이
  로컬에만 있어요`**. 데이터는 이미 있다(`updated_at > _lastBackupAt` 인 행 수 = 아웃박스가
  이미 세는 것과 같은 질의). **새 기계 0 · 새 저장값 0.**

## ⚠ 이 절의 자기 판정
