**0-E 상세 — 1단계의 하드 차단 전제(v2 승격).**
`navigator.storage` API 를 한 번도 호출하지 않는다(`persist()`·`estimate()` 0회) → 저장소가 **best-effort 등급**이라 축출 가능.
① 부팅 시 `storage.persist()` ② `estimate()` 80% 사전 경고 ③ **`exportSnapshot` 범위 정정** — `atlas.notes`·`atlas.stars`(직접 쓴 진로 메모)·`lh:research-history`·`lh_ui_v1` 이 **어떤 백업에도 안 들어간다**.

> ⚠ **v1 은 이걸 "Tauri 후 무의미해질 보험"으로 적었다. 틀렸다.** §4-1단계 C5 참조 — Tauri WebView2 는 Chrome 과 **별개 저장소 오리진**이라 기존 데이터를 자동으로 못 읽는다. 이행은 반드시 **수동 export → import** 이고, ③이 완료되기 전에 1단계로 넘어가면 **아틀라스 메모가 영구 유실**된다.

**0-E 구현 결과 (2026-07-19 · 게이트 녹색).**

- ①② `lib/durability.ts`(`ensureDurableStorage` = `persisted()`→`persist()` 승격 + `estimate()` 병렬) + `app/StorageGuard.tsx`(부팅 1회). **승격 실패는 조용히 넘긴다** — 사용자가 할 수 있는 일이 없고(브라우저 참여도 휴리스틱) 매 부팅 경고는 무시를 학습시킨다. 행동이 필요한 **쿼터 80% 초과만** 토스트(내보내기 액션 동봉). `BootRecovery` 와 분리한 이유: 저기는 "부팅이 기본값으로 떨어졌을 때만" 도는 계약이라 정상 부팅에서 즉시 return 한다.
- ③ `lib/sidecars.ts` — 4개 키를 `_local` 사이드카로. **`_reads` 와 같은 관용구, 별개 층**(저기는 IDB 미러·전용 스키마를 가진 데이터 레이어, 여기는 평문 KV 값 통짜 보존). I1 호환: `_local` 은 **추가 키**라 구 앱이 무시하고, 구 백업엔 없어 `importLocalExtras` 가 no-op.
- **가져오기는 화이트리스트**(`LOCAL_EXTRA_KEYS`) + `Object.hasOwn`. 백업 파일은 신뢰 불가 입력이라 임의 키 쓰기를 허용하면 파일 하나로 `study_planner_v3` 를 덮을 수 있었다.
- ⚠ **설계에 없던 필수 발견 — 복원 후 되읽기.** 4개 키의 소비자(`Atlas` useState · `Control` useState · `useUI`)는 전부 **부팅 시 1회 read** 라, KV 만 복원하면 낡은 메모리가 다음 편집의 `writeJSON`/`flush` 에서 **방금 되살린 메모를 통째로 덮는다**(복원이 데이터 유실로 뒤집힌다). → `SyncMsg` 에 `kind:'local'` 추가, `Atlas`·`Control` 구독 + `useUI.reloadUI()` 명시 호출.
- 부수: 내보내기 페이로드를 `backupPayload()` SSOT 로 수렴 — 파일 내보내기와 볼트 백업이 각자 조립하던 탓에 사이드카가 한쪽에만 붙을 수 있었다.

1. **MSI 번들 실패 — 코드페이지 1252.** `targets:"all"` 이 WiX MSI 를 만드는데, MSI 문자열은 컬처(`en-us`)에 묶인 **코드페이지 1252** 로 들어가 productName `러닝허브` 가 `LGHT0311` 로 링크 실패한다(17건). exe 자체는 정상 빌드되고 **번들 단계에서만** 죽어 "빌드 됐다"로 오인하기 쉽다.

3. **고아 sidecar — `single-instance` 로는 안 덮인다.** 앱이 **강제 종료·크래시**로 죽으면 `Destroyed` 가 안 불려 node 가 포트 8000 을 물고 살아남는다(실측). 그 상태로 재실행하면 새 serve.js 가 `EADDRINUSE` 로 즉사하고 앱은 이유 없이 오프라인 UI 로 뜬다.

**⚠ §8 "동기 flush 계약 파괴" — 1단계 전제가 실측으로 뒤집혔다(v2 → v3 정정).**

설계는 "**Tauri 창 닫기에서 `pagehide` 발화가 보장되지 않는다**"를 근거로 1단계에 셸 전용 닫기 훅을 요구했다. 실제로 만들어 넣었다가 **측정하고 되돌렸다**.

- **측정**: 창 닫기(WM_CLOSE) 때 WebView2 가 실제로 쏘는 이벤트를 세어 보니 `{"beforeunload":1,"visibilitychange:hidden":1,"pagehide":1,"unload":1}` — **전부 발화한다.** 즉 `useApp` 의 기존 브라우저 안전망이 셸에서도 그대로 걸린다.
- **결정적 증거**: 훅을 **비활성화한 빌드**로 "종료 시 flush" e2e 를 돌렸더니 **그대로 통과했다.** 훅이 없어도 편집이 살아남는다 = 1단계에서 훅은 **순수 잉여**.
- **되돌린 이유**: 그 잉여를 위해 `core:window:allow-destroy` 를 열고 강제 파괴 워치독을 달아야 했는데, 그 조합이 위 결함 2번(**창이 안 닫힘**)을 실제로 만들었다. **측정되지 않은 이득을 위해 "앱이 안 닫힐 수 있는" 실패 경로를 새로 만드는 거래**였다.
- **남긴 것**: `lib/tauri.ts`·`capabilities/default.json` 주석에 측정 결과와 **2단계 복귀 조건**을 박아뒀다. ⚠ **2단계에서 flush 가 비동기(invoke)가 되면 다시 필요해진다** — `pagehide` 는 **동기 핸들러만** 보장해서 `await` 가 잘린다. 그때 훅을 되살리며 `allow-destroy` 를 함께 켤 것.

> 교훈은 "설계가 틀렸다"가 아니라 **"보장되지 않는다"와 "발화하지 않는다"는 다른 명제**라는 것이다. 전자는 명세의 진술이고 후자는 관측이다. 전자를 근거로 후자를 가정하면, 검증 없이 복잡도를 산다.

**트랙 B 신설 — `tauri-driver` 대신 CDP + 기존 Playwright.**
설계는 `tauri-driver`(WebDriver·WebdriverIO)를 적었지만, WebView2 가 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` 를 존중해 `--remote-debugging-port` 로 **CDP 를 연다**는 걸 실측했다 → **이미 있는 Playwright 로 진짜 WebView2 를 그대로 운전**한다. tauri-driver + WebdriverIO + Edge WebDriver 세 개를 안 들이고 같은 커버리지를 얻고, 디버그 포트는 하네스만 켜므로 **배포본 노출이 0**(코드 변경 없이 env 로만 제어).

**A-2. I1(export/import JSON 계약) 유지 방법.**
export/import 는 **JSON 그대로 둔다.** 저장소가 바뀌어도 파일 형식은 안 바뀐다 — 그게 I1 이다. 구현은 경계 함수 2개로 좁힌다:

```
DB ──readState()──▶ AppState ──exportSnapshot()──▶ 백업 JSON   (기존 경로 무변경)
백업 JSON ──migrate()→sanitizeImported()──▶ AppState ──writeState()──▶ DB
```

즉 **`AppState` 가 계속 중앙 표현**이고 SQLite 는 그 아래 sink 일 뿐이다. `migrate`·`sanitizeImported`·`exportSnapshot` 은 한 줄도 안 바뀐다(위 정정표 4행과 정합). 새로 생기는 건 `readState`/`writeState` 매퍼 한 쌍뿐이고, `importRoundtripLarge.test.ts`(2단계-0)가 **저장소 교체 전후로 동일하게 통과**해야 하는 것이 이 설계의 판정 기준이다.

**A-3. 동기/비동기 계약 — 가장 위험한 지점.** ⚠
`kv.ts:19` 의 `storage` 는 **모듈 로드 시점에 결정되는 동기 상수**고, `boot()`·`persist()` 가 전부 동기다. SQLite 는 비동기라 정면 충돌한다. 먼저 깨지는 곳 3군데:

1. `useApp.ts:167` — `create()` 내부에서 `state: bootSafely()` 를 **동기 호출**
2. `useApp.ts:151` — `onSync` 가 rebase 때 동기 `boot(storage)` 로 통째 재부팅
3. `useApp.ts:136-141` — `pagehide` 동기 flush(1단계에서 훅을 되돌린 근거가 "동기라서 됐다"였다 → **2단계-C 에서 되살려야 한다**)

**결정: 부팅을 React 마운트 앞으로 옮긴다(하이드레이션 게이트 아님).**
`main.tsx` 가 `await initStore()` 후 `createRoot().render()` 한다. 게이트 컴포넌트 방식(초기값 `defaults()` + `hydrated` 플래그)을 **탈락**시킨 이유: 게이트는 "하이드레이션 전에 쓰기가 일어나면 기본값이 실데이터를 덮는다"는 **새 실패 모드**를 만드는데, 그건 0단계-E 에서 이미 한 번 물린 부류다(_낡은 메모리가 복원본을 덮는다_). 마운트 전 await 는 그 창 자체를 없앤다. 대가는 로컬 SQLite 읽는 동안의 빈 창인데, 같은 기계의 파일이라 짧다.

- rebase(②)는 **디스크 재부팅이 불필요**해진다 — 행 단위 저장이라 다른 탭의 쓰기가 이미 행에 있다. 다만 브라우저 경로 은퇴(2단계-E) 전까지는 멀티탭이 살아 있으므로 `onSync` 를 async 로 바꿔 유지하고, 은퇴 후 BroadcastChannel 과 함께 정리한다(4단계 항목과 합류).
- `pending` recipe 큐는 **유지**한다. semantic-op 재적용은 스냅샷 LWW 보다 강하고 행 모델과 궁합이 좋다(`useApp.ts:104-109` 의 이중 손실 사고 기록이 이 큐의 존재 이유다).

**A-4. `AnkiPanel.tsx:32,97` 을 먼저 계층 안으로.**
유일한 kv SSOT 우회(`lh:anki-autorefresh`, 평문 `'1'`/`'0'`)라 이행 표면 밖에 있고, **어떤 백업에도 안 들어간다**(0단계-E 가 고친 결함과 정확히 같은 부류인데 그때 누락됨). 2단계-B 착수 전에 `useUI` 로 흡수한다.

**A-5. 단계 내 순서.** A(설계) → **A-4**(Anki 키 흡수) → B(플러그인·매퍼·`initStore`) → C(비동기 flush + `allow-destroy`) → D(양방향 대조) → E(JSON 경로 제거 + 브라우저 은퇴) → F(문서·커버리지).

#### 2단계-E/F 완료 (2026-07-19) — 정본 전환 · 증분 쓰기 · 실행기 은퇴

> ⚠ **사용자 지시로 실사용 대조 누적(아래 ①) 없이 E 로 진행했다.** 아래 "착수 전제"는 ②③④가 충족됐고 ①은 **의도적으로 건너뛴** 상태다. 대신 실행 검증(트랙 B)과 순수 테스트를 두껍게 깔았다.

- **정본 전환** — 셸에선 앱 상태를 localStorage 에 쓰지 않는다(IDB 미러도 안 건다: 그 층의 위협모델이 셸엔 없다). `lib/db/boot.ts` 가 부팅에 읽고, 빈 DB 는 **"새 사용자"가 아니라 "아직 이관 안 됨"**으로 읽어 localStorage 에서 1회 이관한다. 모든 실패 경로가 localStorage 폴백으로 수렴한다.
- ⚠ **"브라우저 경로 은퇴"의 범위를 정정했다.** 문자 그대로 하면 `npm run dev` 와 **트랙 A(스냅샷 59장)가 함께 죽는다** — 둘 다 Chromium 이라 SQLite 가 없다. 설계도 이 구분을 안 했다. → **배포 진입점만** 셸 하나로 좁히고(`러닝허브_실행.bat` = 안내 스텁으로 은퇴), localStorage 는 **개발·검증 백엔드로 잔존**한다.

**▶ 실측으로 잡은 결함 2건 — 둘 다 "빌드 녹색인데 아무것도 저장 안 됨"**

1. **SQLITE_BUSY** — `tauri-plugin-sql` 은 sqlx **커넥션 풀**이라 별도 `execute` 로 부른 `BEGIN` 이 다른 커넥션의 쓰기를 막아 `database is locked` 로 죽었다. (첫 프로브는 통과해 이 가설을 한 번 기각했다 — 프로브가 커넥션 1개를 순차 재사용했기 때문. 앱은 `readRows` 가 `Promise.all` 로 여러 커넥션을 잡는다.)
   → **전량 DELETE+INSERT 를 버리고 증분 upsert 로 전환.** 트랜잭션이 필요 없어지고(각 문장이 독립적으로 안전) **DB 가 비는 창도 사라진다**. 중간에 죽어도 남는 건 "여분의 옛 행"이지 "사라진 행"이 아니다. **덤으로 요구사항 ④가 실제로 달성됐다** — 완료 500일 중 1건 수정 시 SQL 문장 **1개**(테스트로 잠금).
2. **읽기가 쓰기를 막던 문제** → `journal_mode=WAL`. "닫기 직전에 상태를 읽으면 그 다음 쓰기가 통째로 실패"하는 형태로 드러났다.

> **두 결함 다 내 코드가 실패를 삼켜서 원인을 못 찾았다.** `getDb`·`writeRows`·`dual` 이 전부 조용히 false 를 돌려주고 있었다 → error 로그를 넣고 나서야 30초 만에 원인이 나왔다. **정본을 쥔 층의 침묵은 그 자체가 결함이다.**

**트랙 B 정리 — "종료 시 flush" 를 `2단계-C` 케이스로 통합.**
같은 계약을 두 벌로 재고 있었다. 그리고 그쪽의 midflight 관측(닫기 직전 저장소를 읽어 "아직 저장 전"을 확인)은 정본이 SQLite 가 되면서 **관측 행위가 관측 대상을 바꿨다** — 그 읽기가 디바운스 400ms 보다 오래 걸린다. 경과시간으로 가두려는 시도도 실패했다(`closeShell` 자체가 400ms 초과). 애초에 취약 구간은 디바운스가 아니라 **SQL 쓰기 소요시간**이라 시간으로 가둘 대상이 아니었다. → 판별력은 **경험적으로** 확인한다: 가드 없던 빌드에서 빨간불, 가드 넣자 녹색.

**F — 문서·커버리지.** `아키텍처.md` §3-1(저장 백엔드 2종) 신설 · `기능추가.md` **"디스크 JSON 형태 불변" 정정**(불변인 건 `AppState` 형태와 내보내기 JSON 이다) · `CLAUDE.md` 실행 경로/레이어. **커버리지 재기준선(이월 ③)은 불필요로 판명** — 설계는 "Tauri 래퍼가 분모를 늘려 임계를 낮춰야 한다"고 봤지만 실측은 **올랐다**(새 코드가 순수 매퍼라 잘 덮였다). 임계 유지.

**남은 것 재검토 (3단계 착수 시 · 결론: 대부분 안 옮긴다)**
2단계 말미에 "`BACKUP_KEY`·`CORRUPT_KEY`·`_reads` 도 SQLite 로 옮기는 게 일관적"이라 적었다. 3단계 착수 전에 다시 보니 **일관성 말고는 근거가 없고, 하나는 오히려 옮기면 안 된다.**

- **`BACKUP_KEY`(되돌리기)·`CORRUPT_KEY`(손상 원본) — 옮기지 않는다.** 이건 **복구 수단**이고, 복구본을 정본과 **다른 매체**에 두는 건 결함이 아니라 성질이다. SQLite 파일이 깨지는 상황에서 되돌리기 백업이 같은 파일 안에 있으면 함께 죽는다. IDB 미러를 두던 것과 같은 위협모델이다. 쿼터도 문제없다 — 정본(KEY)이 빠져서 상주량이 대용량 표본 기준 ≈3.04MB → **≈1.5MB** 로 내려갔다.
- **`_reads`(내 요약·독후감) — 미룬다(3단계 범위 밖).** 이건 복구본이 아니라 **사용자 저작물**이라 정본과 같은 곳에 있는 게 맞다. 다만 `loadReads()` 가 **동기**이고 팔레트·Reads 탭이 렌더 경로에서 부른다 — 옮기려면 `initAppStore` 때 메모리로 끌어올려 동기 시그니처를 유지하는 작업이 붙는다(`preloadedState` 와 같은 관용구). 현재 크기가 0.1MB 수준이라 **지금 갚을 이유가 없는 빚**이고, 4단계에서 `lib/reads.ts` 가 어차피 손댈 파일이라 그때 합친다.

> 교훈: "일관적이다"는 그 자체로 작업 근거가 아니다. 이 항목을 그대로 실행했으면 **복구 수단을 정본과 한 바구니에 담는 퇴행**을 "정리"라는 이름으로 했을 것이다.

**E 착수 전 충족해야 했던 것 (①만 미충족 상태로 진행)**

1. **실사용 세션 누적** — 평소처럼 앱을 쓰면서 설정 탭의 대조 줄이 계속 녹색인지. 특히 아직 한 번도 안 타본 경로(가져오기·되돌리기·IDB 복구·아카이빙·오래된 기록 정리).
2. **부팅 읽기 경로** — 지금 `getDb()` 는 **지연 로드**라 편집이 없던 세션은 DB 를 아예 안 연다(트랙 B 에서 `database not loaded` 로 드러났다). E 는 부팅에 읽어야 하므로 `main.tsx` 의 `await initStore()` 가 필요하다(A-3).
3. **대용량 이관 왕복을 셸에서 1회** — 2단계-0 의 잔여(jsdom 에서만 검증됨). 브라우저 경로를 은퇴시키면 **더 이상 리허설할 수 없다.**

## 10. 탈락시킨 대안

- **원격 서버 + DB** — 내구성만이면 **앱이 소유한 로컬 파일**(2단계)이 더 안전하고 싸다. 그리고 원격으로 가도 **볼트는 여전히 로컬**이다(`knowledge/` 마크다운을 이 기계에서 Obsidian 으로 편집하고 `pipeline/` 파이썬이 직접 읽는다 — 동기하려면 Dropbox 를 직접 만드는 일). 네트워크 노출은 인증·세션·CSRF·TLS·백업 운영을 사용자 1명을 위해 세우게 한다.
- **Next.js/RSC** — 서버 유무와 무관하게 값이 없다: SEO 없음 · 낯선 방문자 없음 · 사용자 1명이라 SSR 이 아낄 TTFB 가 없음 · **렌더할 데이터가 서버에 없다**(소유권이 클라이언트).
- **OPFS + wa-sqlite(WASM) + Worker** — Rust 없이 SQLite·Worker 이득을 대부분 얻는 유력 후보. 탈락: 2프로세스 실행이 남고 **File System Access API 에 watch 가 없어 파일 감시가 불가능**(§4-3단계가 제품 성격 변경이라 판단한 기능).
- **Electron** — 무겁고 Node 런타임을 안고 간다.
- **SonarQube Server/Cloud** — 룰은 `eslint-plugin-sonarjs` 로 인프라 0에 얻는다(§0-F). 서버가 더 주는 건 대시보드·추세뿐이고 Cloud 는 소스가 제3자로 나간다. 추세가 필요해지면 나중에 얹어도 룰 엔진이 같아 재작업 없음.
- **전면 재작성** — N1. 고점을 내리는 유일한 경로.
- **Tailwind 를 "안 함"** — 원래 판단이었으나 **사용자 지시로 6단계 채택**. 근거 정정도 기록: 처음엔 "레이아웃 기하가 복잡해 Tailwind 가 약하다"고 했으나 실측하니 calc/clamp/grid 는 158개(2%)뿐이라 **그 논거는 틀렸다**. 실제 마찰은 관계형 셀렉터 1,904개다.
