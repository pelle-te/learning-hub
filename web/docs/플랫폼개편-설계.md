## 0. 요약

구조적 결함이 두 뿌리에서 나온다 — **데스크톱 워크로드를 브라우저 샌드박스에서 돌리고 있고, 앱 데이터가 JSON 덩어리 하나다.** 프레임워크(React 19 · Vite · zustand)와 도메인 로직(`features/` 27,219줄 · `lib/scheduler/`)은 손대지 않고 **그 아래 플랫폼·데이터 모델·스타일 레이어만** 교체한다.

셸      브라우저 + .bat 2프로세스   →  Tauri 2 단일 바이너리            1 ✅
프런트  React19 · Vite · zustand   →  그대로 (무변경)                  —  ✅ 지켜짐

볼트    메인스레드 풀스캔·수동버튼   →  Rust 인덱스 읽기 + notify 감시   3 ✅
백엔드  serve.js 856줄(무테스트)    →  Rust 커맨드(포트 0)              4 ✅
모바일  없음                       →  읽기 전용 뷰(방식 미결정)         5

> **v4 갱신.** 1~4단계 완료(2026-07-19). 두 칸의 _목표_ 표현도 실제에 맞게 고쳤다 —
> 볼트는 **증분 스캔이 아니라 "인덱스가 있으면 순회 자체가 없다"** 로 끝났고(3단계: 증분이

**0-E 상세 — 1단계의 하드 차단 전제(v2 승격).**
`navigator.storage` API 를 한 번도 호출하지 않는다(`persist()`·`estimate()` 0회) → 저장소가 **best-effort 등급**이라 축출 가능.
① 부팅 시 `storage.persist()` ② `estimate()` 80% 사전 경고 ③ **`exportSnapshot` 범위 정정** — `atlas.notes`·`atlas.stars`(직접 쓴 진로 메모)·`lh:research-history`·`lh_ui_v1` 이 **어떤 백업에도 안 들어간다**.

> ⚠ **v1 은 이걸 "Tauri 후 무의미해질 보험"으로 적었다. 틀렸다.** §4-1단계 C5 참조 — Tauri WebView2 는 Chrome 과 **별개 저장소 오리진**이라 기존 데이터를 자동으로 못 읽는다. 이행은 반드시 **수동 export → import** 이고, ③이 완료되기 전에 1단계로 넘어가면 **아틀라스 메모가 영구 유실**된다.

**0-E 구현 결과 (2026-07-19 · 게이트 녹색).**

- ①② `lib/durability.ts`(`ensureDurableStorage` = `persisted()`→`persist()` 승격 + `estimate()` 병렬) + `app/StorageGuard.tsx`(부팅 1회). **승격 실패는 조용히 넘긴다** — 사용자가 할 수 있는 일이 없고(브라우저 참여도 휴리스틱) 매 부팅 경고는 무시를 학습시킨다. 행동이 필요한 **쿼터 80% 초과만** 토스트(내보내기 액션 동봉). `BootRecovery` 와 분리한 이유: 저기는 "부팅이 기본값으로 떨어졌을 때만" 도는 계약이라 정상 부팅에서 즉시 return 한다.
- ③ `lib/sidecars.ts` — 4개 키를 `_local` 사이드카로. **`_reads` 와 같은 관용구, 별개 층**(저기는 IDB 미러·전용 스키마를 가진 데이터 레이어, 여기는 평문 KV 값 통짜 보존). I1 호환: `_local` 은 **추가 키**라 구 앱이 무시하고, 구 백업엔 없어 `importLocalExtras` 가 no-op.
- **가져오기는 화이트리스트**(`LOCAL_EXTRA_KEYS`) + `Object.hasOwn`. 백업 파일은 신뢰 불가 입력이라 임의 키 쓰기를 허용하면 파일 하나로 `study_planner_v3` 를 덮을 수 있었다.
- ⚠ **설계에 없던 필수 발견 — 복원 후 되읽기.** 4개 키의 소비자(`Atlas` useState · `Control` useState · `useUI`)는 전부 **부팅 시 1회 read** 라, KV 만 복원하면 낡은 메모리가 다음 편집의 `writeJSON`/`flush` 에서 **방금 되살린 메모를 통째로 덮는다**(복원이 데이터 유실로 뒤집힌다). → `SyncMsg` 에 `kind:'local'` 추가, `Atlas`·`Control` 구독 + `useUI.reloadUI()` 명시 호출.
- 부수: 내보내기 페이로드를 `backupPayload()` SSOT 로 수렴 — 파일 내보내기와 볼트 백업이 각자 조립하던 탓에 사이드카가 한쪽에만 붙을 수 있었다.
- 테스트: `test/sidecars.test.ts`(왕복·화이트리스트·프로토타입·구 백업 no-op·쿼터 실패) · `test/durability.test.ts`(미지원·재요청 안 함·reject 흡수·quota 0).

2. **⚠ 창이 영영 안 닫힌다 — `core:window:default` 는 조회 전용.** 프런트가 `onCloseRequested` 를 등록하면 Tauri 는 닫기를 **보류**하고 `destroy()` 를 기다린다. 그런데 `core:default` 안의 `core:window:default` 는 `allow-get-*`·`allow-is-*` 같은 **조회 권한만** 있고 `allow-destroy` 가 없다 → destroy 가 ACL 에 막혀 **창이 닫히지 않는다**(실측: `CloseMainWindow` 후 5초, 프로세스 생존).

   > 설계 시점의 판단 **"리스너가 없으면 평소대로 닫히니 안전망이 앱을 못 닫게 만들 수는 없다"는 틀렸다.** 등록은 성공하는데 _파괴만_ 거부되는 3번째 상태가 있다.
   > → **1단계에서는 이 훅 자체를 안 쓰기로 했다**(아래 §"창 닫기 안전망" 참조). 대신 `capabilities/default.json` 주석에 경고를 남겼다: **2단계에서 `onCloseRequested` 를 되살리는 순간 `core:window:allow-destroy` 를 함께 켜야 한다.** 안 켜면 앱이 안 닫힌다.

3. **고아 sidecar — `single-instance` 로는 안 덮인다.** 앱이 **강제 종료·크래시**로 죽으면 `Destroyed` 가 안 불려 node 가 포트 8000 을 물고 살아남는다(실측). 그 상태로 재실행하면 새 serve.js 가 `EADDRINUSE` 로 즉사하고 앱은 이유 없이 오프라인 UI 로 뜬다.
   → 설계가 "`.bat` 의 taskkill → `single-instance` 로 흡수"라 적은 건 **정상 중복 실행만** 덮는다. `sidecar::spawn` 에 **고아 선점 처리** 신설: `/api/ping` 으로 우리 serve.js 인지 확인 → **워크스페이스가 같으면 재사용(입양), 다르면 교체**. 무조건 죽이지 않는 이유는 재기동이 순수 손해(부팅 지연 + 진행 중 파이썬 잡 사망)이고, 반대로 워크스페이스가 다르면 반드시 죽여야 하는 이유는 낡은 `LH_WORKSPACE` 서버가 파이썬 도구 11종을 **조용히 빈 결과**로 만들기 때문이다(가장 진단하기 어려운 실패).
   - **입양(adopt)**: 재사용한 고아의 PID 를 들고 있다가 종료 때 함께 내린다. 없으면 "재사용한 세션은 앱을 닫아도 node 가 영원히 남는다"가 된다(실측 후 추가).
   - ⚠ **probe 의 Host 헤더는 포트까지 보내야 한다** — `serve.js:526 hostOK` 가 DNS 리바인딩 방어로 `127.0.0.1:8000` **정확 일치**를 요구한다(0단계-A 가 잠근 계약). 포트를 빼면 403 이 와서 probe 가 "우리 서버 아님"으로 **오판**하고 고아를 못 알아본다. 방어를 약화시키는 게 아니라 probe 가 계약을 지키는 방향으로 맞췄다.

**⚠ §8 "동기 flush 계약 파괴" — 1단계 전제가 실측으로 뒤집혔다(v2 → v3 정정).**

설계는 "**Tauri 창 닫기에서 `pagehide` 발화가 보장되지 않는다**"를 근거로 1단계에 셸 전용 닫기 훅을 요구했다. 실제로 만들어 넣었다가 **측정하고 되돌렸다**.

- **측정**: 창 닫기(WM_CLOSE) 때 WebView2 가 실제로 쏘는 이벤트를 세어 보니 `{"beforeunload":1,"visibilitychange:hidden":1,"pagehide":1,"unload":1}` — **전부 발화한다.** 즉 `useApp` 의 기존 브라우저 안전망이 셸에서도 그대로 걸린다.
- **결정적 증거**: 훅을 **비활성화한 빌드**로 "종료 시 flush" e2e 를 돌렸더니 **그대로 통과했다.** 훅이 없어도 편집이 살아남는다 = 1단계에서 훅은 **순수 잉여**.
- **되돌린 이유**: 그 잉여를 위해 `core:window:allow-destroy` 를 열고 강제 파괴 워치독을 달아야 했는데, 그 조합이 위 결함 2번(**창이 안 닫힘**)을 실제로 만들었다. **측정되지 않은 이득을 위해 "앱이 안 닫힐 수 있는" 실패 경로를 새로 만드는 거래**였다.
- **남긴 것**: `lib/tauri.ts`·`capabilities/default.json` 주석에 측정 결과와 **2단계 복귀 조건**을 박아뒀다. ⚠ **2단계에서 flush 가 비동기(invoke)가 되면 다시 필요해진다** — `pagehide` 는 **동기 핸들러만** 보장해서 `await` 가 잘린다. 그때 훅을 되살리며 `allow-destroy` 를 함께 켤 것.

> 교훈은 "설계가 틀렸다"가 아니라 **"보장되지 않는다"와 "발화하지 않는다"는 다른 명제**라는 것이다. 전자는 명세의 진술이고 후자는 관측이다. 전자를 근거로 후자를 가정하면, 검증 없이 복잡도를 산다.

**트랙 B 신설 — `tauri-driver` 대신 CDP + 기존 Playwright.**
설계는 `tauri-driver`(WebDriver·WebdriverIO)를 적었지만, WebView2 가 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` 를 존중해 `--remote-debugging-port` 로 **CDP 를 연다**는 걸 실측했다 → **이미 있는 Playwright 로 진짜 WebView2 를 그대로 운전**한다. tauri-driver + WebdriverIO + Edge WebDriver 세 개를 안 들이고 같은 커버리지를 얻고, 디버그 포트는 하네스만 켜므로 **배포본 노출이 0**(코드 변경 없이 env 로만 제어).

**A-2. I1(export/import JSON 계약) 유지 방법.**
export/import 는 **JSON 그대로 둔다.** 저장소가 바뀌어도 파일 형식은 안 바뀐다 — 그게 I1 이다. 구현은 경계 함수 2개로 좁힌다:

```
DB ──readState()──▶ AppState ──exportSnapshot()──▶ 백업 JSON   (기존 경로 무변경)
백업 JSON ──migrate()→sanitizeImported()──▶ AppState ──writeState()──▶ DB
```

즉 **`AppState` 가 계속 중앙 표현**이고 SQLite 는 그 아래 sink 일 뿐이다. `migrate`·`sanitizeImported`·`exportSnapshot` 은 한 줄도 안 바뀐다(위 정정표 4행과 정합). 새로 생기는 건 `readState`/`writeState` 매퍼 한 쌍뿐이고, `importRoundtripLarge.test.ts`(2단계-0)가 **저장소 교체 전후로 동일하게 통과**해야 하는 것이 이 설계의 판정 기준이다.

**A-3. 동기/비동기 계약 — 가장 위험한 지점.** ⚠
`kv.ts:19` 의 `storage` 는 **모듈 로드 시점에 결정되는 동기 상수**고, `boot()`·`persist()` 가 전부 동기다. SQLite 는 비동기라 정면 충돌한다. 먼저 깨지는 곳 3군데:

1. `useApp.ts:167` — `create()` 내부에서 `state: bootSafely()` 를 **동기 호출**
2. `useApp.ts:151` — `onSync` 가 rebase 때 동기 `boot(storage)` 로 통째 재부팅
3. `useApp.ts:136-141` — `pagehide` 동기 flush(1단계에서 훅을 되돌린 근거가 "동기라서 됐다"였다 → **2단계-C 에서 되살려야 한다**)

**결정: 부팅을 React 마운트 앞으로 옮긴다(하이드레이션 게이트 아님).**
`main.tsx` 가 `await initStore()` 후 `createRoot().render()` 한다. 게이트 컴포넌트 방식(초기값 `defaults()` + `hydrated` 플래그)을 **탈락**시킨 이유: 게이트는 "하이드레이션 전에 쓰기가 일어나면 기본값이 실데이터를 덮는다"는 **새 실패 모드**를 만드는데, 그건 0단계-E 에서 이미 한 번 물린 부류다(_낡은 메모리가 복원본을 덮는다_). 마운트 전 await 는 그 창 자체를 없앤다. 대가는 로컬 SQLite 읽는 동안의 빈 창인데, 같은 기계의 파일이라 짧다.

- rebase(②)는 **디스크 재부팅이 불필요**해진다 — 행 단위 저장이라 다른 탭의 쓰기가 이미 행에 있다. 다만 브라우저 경로 은퇴(2단계-E) 전까지는 멀티탭이 살아 있으므로 `onSync` 를 async 로 바꿔 유지하고, 은퇴 후 BroadcastChannel 과 함께 정리한다(4단계 항목과 합류).
- `pending` recipe 큐는 **유지**한다. semantic-op 재적용은 스냅샷 LWW 보다 강하고 행 모델과 궁합이 좋다(`useApp.ts:104-109` 의 이중 손실 사고 기록이 이 큐의 존재 이유다).

**A-4. `AnkiPanel.tsx:32,97` 을 먼저 계층 안으로.**
유일한 kv SSOT 우회(`lh:anki-autorefresh`, 평문 `'1'`/`'0'`)라 이행 표면 밖에 있고, **어떤 백업에도 안 들어간다**(0단계-E 가 고친 결함과 정확히 같은 부류인데 그때 누락됨). 2단계-B 착수 전에 `useUI` 로 흡수한다.

**A-5. 단계 내 순서.** A(설계) → **A-4**(Anki 키 흡수) → B(플러그인·매퍼·`initStore`) → C(비동기 flush + `allow-destroy`) → D(양방향 대조) → E(JSON 경로 제거 + 브라우저 은퇴) → F(문서·커버리지).

설계 §8 의 "비동기 flush 는 `pagehide` 에서 잘린다"를 **믿지 않고 쟀다** — 1단계에서 같은 형태의 추론이 실측에 뒤집혀 훅을 만들었다 되돌린 이력이 있기 때문이다.

> **측정 결과: 실제로 잘린다.** 트랙 B `2단계-C` 케이스 — 디바운스 대기 중 창을 닫으면 동기 localStorage 는 `pagehide` 로 지켜지지만 **비동기 SQL 쓰기는 통째로 유실**된다. 1단계와 **정반대 결과**라, 같은 형태의 명제라도 매번 재봐야 한다는 것이 오히려 강화됐다.

- **안전 속성을 저장보다 우선**했다: `beforeClose` 가 던지든 · 영영 안 끝나든(3초 타임아웃) · 훅 등록이 실패하든 **창은 반드시 닫힌다**. `test/closeGuard.test.ts` 5케이스가 잠근다. 1단계에서 이 가드가 실제로 앱을 못 닫게 만든 적이 있어서다.

`lib/db/dual.ts` — localStorage 가 **아직 정본**이고 SQLite 는 나란히 기록 후 되읽어 슬라이스 단위로 대조한다. flush 를 막지 않고(await 안 함), 실패해도 flush 를 실패로 만들지 않는다. 설정 탭에 진단 한 줄(`ParityLine`), 트랙 B 에 실 WebView2 대조 케이스.

#### 2단계-E/F 완료 (2026-07-19) — 정본 전환 · 증분 쓰기 · 실행기 은퇴

> ⚠ **사용자 지시로 실사용 대조 누적(아래 ①) 없이 E 로 진행했다.** 아래 "착수 전제"는 ②③④가 충족됐고 ①은 **의도적으로 건너뛴** 상태다. 대신 실행 검증(트랙 B)과 순수 테스트를 두껍게 깔았다.

- **정본 전환** — 셸에선 앱 상태를 localStorage 에 쓰지 않는다(IDB 미러도 안 건다: 그 층의 위협모델이 셸엔 없다). `lib/db/boot.ts` 가 부팅에 읽고, 빈 DB 는 **"새 사용자"가 아니라 "아직 이관 안 됨"**으로 읽어 localStorage 에서 1회 이관한다. 모든 실패 경로가 localStorage 폴백으로 수렴한다.
- ⚠ **"브라우저 경로 은퇴"의 범위를 정정했다.** 문자 그대로 하면 `npm run dev` 와 **트랙 A(스냅샷 59장)가 함께 죽는다** — 둘 다 Chromium 이라 SQLite 가 없다. 설계도 이 구분을 안 했다. → **배포 진입점만** 셸 하나로 좁히고(`러닝허브_실행.bat` = 안내 스텁으로 은퇴), localStorage 는 **개발·검증 백엔드로 잔존**한다.

**▶ 실측으로 잡은 결함 2건 — 둘 다 "빌드 녹색인데 아무것도 저장 안 됨"**

1. **SQLITE_BUSY** — `tauri-plugin-sql` 은 sqlx **커넥션 풀**이라 별도 `execute` 로 부른 `BEGIN` 이 다른 커넥션의 쓰기를 막아 `database is locked` 로 죽었다. (첫 프로브는 통과해 이 가설을 한 번 기각했다 — 프로브가 커넥션 1개를 순차 재사용했기 때문. 앱은 `readRows` 가 `Promise.all` 로 여러 커넥션을 잡는다.)
   → **전량 DELETE+INSERT 를 버리고 증분 upsert 로 전환.** 트랜잭션이 필요 없어지고(각 문장이 독립적으로 안전) **DB 가 비는 창도 사라진다**. 중간에 죽어도 남는 건 "여분의 옛 행"이지 "사라진 행"이 아니다. **덤으로 요구사항 ④가 실제로 달성됐다** — 완료 500일 중 1건 수정 시 SQL 문장 **1개**(테스트로 잠금).
2. **읽기가 쓰기를 막던 문제** → `journal_mode=WAL`. "닫기 직전에 상태를 읽으면 그 다음 쓰기가 통째로 실패"하는 형태로 드러났다.

> **두 결함 다 내 코드가 실패를 삼켜서 원인을 못 찾았다.** `getDb`·`writeRows`·`dual` 이 전부 조용히 false 를 돌려주고 있었다 → error 로그를 넣고 나서야 30초 만에 원인이 나왔다. **정본을 쥔 층의 침묵은 그 자체가 결함이다.**

**트랙 B 정리 — "종료 시 flush" 를 `2단계-C` 케이스로 통합.**
같은 계약을 두 벌로 재고 있었다. 그리고 그쪽의 midflight 관측(닫기 직전 저장소를 읽어 "아직 저장 전"을 확인)은 정본이 SQLite 가 되면서 **관측 행위가 관측 대상을 바꿨다** — 그 읽기가 디바운스 400ms 보다 오래 걸린다. 경과시간으로 가두려는 시도도 실패했다(`closeShell` 자체가 400ms 초과). 애초에 취약 구간은 디바운스가 아니라 **SQL 쓰기 소요시간**이라 시간으로 가둘 대상이 아니었다. → 판별력은 **경험적으로** 확인한다: 가드 없던 빌드에서 빨간불, 가드 넣자 녹색.

**F — 문서·커버리지.** `아키텍처.md` §3-1(저장 백엔드 2종) 신설 · `기능추가.md` **"디스크 JSON 형태 불변" 정정**(불변인 건 `AppState` 형태와 내보내기 JSON 이다) · `CLAUDE.md` 실행 경로/레이어. **커버리지 재기준선(이월 ③)은 불필요로 판명** — 설계는 "Tauri 래퍼가 분모를 늘려 임계를 낮춰야 한다"고 봤지만 실측은 **올랐다**(새 코드가 순수 매퍼라 잘 덮였다). 임계 유지.

**남은 것 재검토 (3단계 착수 시 · 결론: 대부분 안 옮긴다)**
2단계 말미에 "`BACKUP_KEY`·`CORRUPT_KEY`·`_reads` 도 SQLite 로 옮기는 게 일관적"이라 적었다. 3단계 착수 전에 다시 보니 **일관성 말고는 근거가 없고, 하나는 오히려 옮기면 안 된다.**

- **`BACKUP_KEY`(되돌리기)·`CORRUPT_KEY`(손상 원본) — 옮기지 않는다.** 이건 **복구 수단**이고, 복구본을 정본과 **다른 매체**에 두는 건 결함이 아니라 성질이다. SQLite 파일이 깨지는 상황에서 되돌리기 백업이 같은 파일 안에 있으면 함께 죽는다. IDB 미러를 두던 것과 같은 위협모델이다. 쿼터도 문제없다 — 정본(KEY)이 빠져서 상주량이 대용량 표본 기준 ≈3.04MB → **≈1.5MB** 로 내려갔다.
- **`_reads`(내 요약·독후감) — 미룬다(3단계 범위 밖).** 이건 복구본이 아니라 **사용자 저작물**이라 정본과 같은 곳에 있는 게 맞다. 다만 `loadReads()` 가 **동기**이고 팔레트·Reads 탭이 렌더 경로에서 부른다 — 옮기려면 `initAppStore` 때 메모리로 끌어올려 동기 시그니처를 유지하는 작업이 붙는다(`preloadedState` 와 같은 관용구). 현재 크기가 0.1MB 수준이라 **지금 갚을 이유가 없는 빚**이고, 4단계에서 `lib/reads.ts` 가 어차피 손댈 파일이라 그때 합친다.

> 교훈: "일관적이다"는 그 자체로 작업 근거가 아니다. 이 항목을 그대로 실행했으면 **복구 수단을 정본과 한 바구니에 담는 퇴행**을 "정리"라는 이름으로 했을 것이다.

#### 3단계 완료 (2026-07-19)

**착수 순서를 바꿨다(사용자 승인).** 설계는 A(Rust 스캐너) 우선이었지만, 표면 조사 결과 **정본 인덱스가 있으면 디렉터리 순회 자체가 없다**(JSON 한 파일 읽기). 즉 Rust 스캐너가 대체할 "메인스레드 풀스캔"은 **평소에 안 도는 경로**였고, 설계가 상시 비용으로 가정한 전제가 성립하지 않았다. 실제 가치 순서는 **감시 → 폴더 선택 제거 → 스캐너**였다.

**3단계-B — 폴백 스캔이 노트 46%를 버리고 있었다(실측).**

| ---------------------- | --------------- |

- 근본 원인은 깊이가 아니라 **집계 구현이 두 벌이었던 것**이다. 인덱스 경로는 `folder` 를 쪼개 임의 깊이를 이미 지원했고 폴백은 별도 3중 루프였다 — 두 경로가 서로 다른 볼트 구조를 지원했고 문서화된 적도 없다. 이제 폴백도 **같은 집계 함수**에 넣어 분기를 없앴고, 덤으로 `verified` 판정(`includes` vs 정확 일치)과 과목 루트 노트 취급도 자동으로 일치했다.
- 남은 오차 1개는 원리적 한계다 — 인덱스는 `kind`(개념노트 454·집합체 62·실전문제 57)로 거르는데 폴백엔 그 정보가 없어 파일명으로 유추한다.

serve.js 는 `RUNNING++` / `Math.max(0, RUNNING-1)` 로 캡을 셌다. 이 형태는 **해제를 빠뜨리거나 두 번 하는 것이 문법적으로 가능**하고, 실제로 그 사고가 있었다(감사 2026-07-16 ①#45 — 프로토타입 키가 콜백을 재실행시켜 `RUNNING` 이중 증가 → `/api/run` 전체가 429 로 영구 마비). 0-A 는 이걸 테스트로 못 덮었다(캡 3개가 라우터 클로저 안 · 실제 429 를 만들려면 python 을 점유해야 함).

- 이제 획득이 `CapGuard` 를 낳고 해제는 `Drop` 이 한다 → **"해제 누락"·"이중 해제"가 표현 불가능**해진다. 조기 return·`?` 전파·패닉 어느 쪽이든 스코프를 벗어나면 정확히 한 번 풀린다. 규율이 아니라 타입이 보장한다.
- `compare_exchange` 루프인 이유: `load` 후 `store` 로 쪼개면 동시 호출이 같은 값을 읽어 **둘 다 통과**한다. 32스레드 동시 획득 테스트가 이걸 잡는다.

**▶ stdout 파서 6종은 이식하지 않았다 — 죽은 코드였다.**
처음엔 "언어를 바꾸면 정규식 의미가 갈리니 TS 로 원문 그대로 옮기자"고 판단해 `lib/toolStats.ts` 를 만들었다. 그런데 옮기는 도중 두 가지가 드러났다.

1. **린터가 즉시 ReDoS 를 잡았다.** `노트 (\d+)개[\s\S]*?전체숙달 …` 가 sonarjs `super-linear-regex` 에 걸렸다 — 0단계-F 가 `vault.ts` 에서 고친 것과 같은 부류다. **serve.js 는 `web/src` 밖이라 이 룰이 한 번도 닿은 적이 없었다.** 결함은 처음부터 있었고 도구 stdout 이 20,000자로 캡돼 있어 폭주까지 안 간 것뿐이다.

> 둘째가 첫째를 설명한다: **아무도 안 읽었기 때문에 그 오류가 드러난 적이 없다.** 읽히지 않는 값을 언어만 바꿔 옮기면 같은 결함을 새 코드에 심는 일이라, `toolStats.ts` 를 지우고 `RunResult.stats` 를 뺐다. 필요해지면 `out` 에서 다시 뽑을 수 있고 그땐 실제 출력을 보고 쓰게 된다.

#### 4단계-E 완료 (2026-07-19) — Ollama 5종 · 스트리밍을 `Channel` 로

`src-tauri/src/ollama.rs` — 코치·어휘·브리핑·회고·임베딩(serve.js L275-504 · L684-717). 프롬프트 빌더 4종·`parseModelJSON`·캡(생성 2 / 임베딩 1)·무소식 90초 타임아웃을 승계했다. HTTP 는 `reqwest`(**TLS 피처 끔** — 대상이 `127.0.0.1:11434` 고정이라 필요가 없고, serve.js 도 `http` 모듈만 썼다).

**스트리밍 = `Channel` 로 델타 + 커맨드 반환값으로 최종.**
serve.js 는 NDJSON 을 HTTP 응답으로 중계했다(`{d}` 줄들 → `{done:true,…}` 줄). IPC 엔 그런 응답 스트림이 없다. 이 배치를 고른 이유는 **`api.ts` 의 기존 계약과 정확히 겹치기 때문**이다 — `postStream` 이 하던 일이 "델타마다 `onDelta`, 끝나면 `T` 반환"이라, 소비 3곳(`ArticlePractice`·`Markets`·`Review`)과 `previewFromJsonStream` 이 **한 줄도 안 바뀌었다.** 그게 4-A 가 정한 판정 기준이었고 충족했다.

- ⚠ **누적은 프런트가 한다.** Rust 는 증분만 보내는데 `StreamOpts.onDelta` 의 계약은 **누적 원문**이다(`previewFromJsonStream` 이 누적을 전제로 값만 뽑는다). 여기서 누적을 빠뜨리면 미리보기가 조각 하나만 보고 깜빡인다 — 에러 없이 UX 만 망가지는 부류라 테스트로 잠갔다.
- ⚠ **`Option<Channel<_>>` 은 컴파일이 안 된다.** `Channel<T>` 는 `Deserialize` 가 아니라 `CommandArg` 로 직접 구현돼 있어서다(`Option` 의 `CommandArg` 는 `Deserialize` 를 거친다). Tauri 가 그 경우를 위해 둔 `JavaScriptChannelId` 를 받아 `channel_on(webview)` 로 바꾼다 — 스트리밍/단발을 한 커맨드로 합치려면 이 우회가 필요하다.

**취소가 이제 진짜로 멈춘다 — 4-C 의 빚을 갚았다.** `AbortSignal` → `ollama_cancel(requestId)` → 스트림 루프가 연결을 끊는다(serve.js 의 `res.on('close')` 와 같은 효과). 4-C 에서 "`invoke` 는 `AbortSignal` 을 안 받는다"며 미뤄 둔 자리다.

**실패는 던지지 않고 봉투에 담는다** — `{ok:false,error}` 를 **값으로** 준다(serve.js 가 200 + `ok:false` 로 하던 것). 소비처가 `.ok` 로 분기하므로 throw 로 바꾸면 그 분기가 죽고 "눌렀는데 아무 일도 안 일어남"이 된다(4-D 와 같은 규율).

**검증**: Rust 12케이스 — 그중 셋이 특히 값을 했다.

- **`<think>` 제거가 비탐욕인가.** 탐욕이면 두 사고 블록 **사이의 본문까지 통째로 먹는다.**
- **`parse_model_json` 의 두 실패가 다르다.** 중괄호 짝이 **없으면** `{raw}`(시도조차 안 함), **있는데 파싱이 깨지면** `None`(= '응답 파싱 실패'). 처음 쓴 테스트가 이걸 헷갈려 실패했는데 **틀린 건 테스트였다** — serve.js 정규식을 다시 읽고 계약대로 고쳤다.
- **봉투 키가 라우트마다 다르다**(`feedback`/`vocab`/`brief`/`coach`). 틀리면 소비처가 값을 못 찾아 **에러 없이 빈 화면**이 된다.

프런트 7케이스(누적 의미론 · `previewFromJsonStream` 맞물림 · 단발 경로에 채널이 안 붙는지 · 취소 전달 · 봉투). **트랙 B 신규 1케이스 — 진짜 qwen3:8b 를 태운다**(12.4초). 여기서만 보이는 것: reqwest 가 실제로 Ollama 와 말하는가 · NDJSON 을 줄 단위로 가르는가 · **Channel 배선이 맞는가**(vitest 는 Channel 을 스텁으로 대체하므로 원리적으로 못 본다). Ollama 가 꺼져 있으면 생성 단언은 건너뛰되 **연결 실패가 봉투로 오는지는 반드시 확인**한다.

### 5단계 — LAN 읽기 전용 모바일 뷰

폰이 PC 의 SQLite 를 직접 읽으므로 **정본 하나, 동기화 없음**. 모바일 UI·브레이크포인트는 이미 존재.

> ## ⚠ v4 정정 — **이 단계의 전제가 4단계 실행으로 뒤집혔다**
>
> v2 는 "**4단계의 Rust HTTP 확장**"이라고 적었다. **성립하지 않는다 — 4단계는 HTTP 서버를 만들지 않았다.** `serve.js` 의 라우트 12종은 HTTP 핸들러가 아니라 **Tauri 커맨드**가 됐고, 그 결과 앱이 여는 포트는 **0** 이다. 확장할 서버가 없다.
>
> **따라서 5단계는 "확장"이 아니라 "신설"이다.** 규모가 v2 가 상정한 것보다 크다는 뜻이고, 착수 전에 아래 3가지를 결정해야 한다.

**5-0. 착수 전 결정 3건 (v4 신설)**

1. **HTTP 서버 크레이트.** 지금 있는 `reqwest` 는 **클라이언트**다 — 서버는 별도로 들여야 한다(`axum` 계열 vs `tiny_http` 급). 4단계가 의존성을 최소로 유지해 온 기조(`reqwest` 도 TLS 피처를 필요해진 뒤에야 켰다)를 이어, **읽기 전용 라우트 몇 개에 필요한 최소한**으로 고를 것.
2. **커맨드 로직 재사용 경로.** 다행히 4단계가 대부분 **순수 함수와 IO 를 갈라 두었다**(`artifact.rs read_at` · `anki_scan.rs scan_at` · `news.rs parse_news_rss` · `ollama.rs build/parse_model_json`). HTTP 핸들러는 이 함수들을 그대로 부르면 되고, **`#[tauri::command]` 함수를 부르면 안 된다**(`AppHandle` 을 요구해 서버 컨텍스트와 안 맞는다). 이 분리가 이미 돼 있다는 것이 5단계의 착수 비용을 크게 낮춘다.
3. **읽기/쓰기 분리 지점.** v2 가 "4단계 Rust 설계 때부터 갈라둘 것"이라 했는데 **4단계는 그 분리를 하지 않았다**(IPC 엔 필요가 없었다). 5단계가 처음부터 해야 한다.

> ### ⚠ v4 신설 — **4-G 대조표에서 "불필요"로 닫은 13건 중 상당수가 여기서 부활한다**
>
> 그 표가 "불필요"라고 한 것은 **"IPC 에서는"** 이지 "영원히"가 아니다. 포트를 다시 여는 순간 되살아나는 것들:
>
> | 4-G 에서 닫은 것                  | 5단계에서의 처지                                               |
> | --------------------------------- | -------------------------------------------------------------- |
> | Host 위조 403(DNS 리바인딩)       | **부활 필수** — `0.0.0.0` 바인딩이면 위험이 오히려 커진다      |
> | 비-로컬 Origin 403(CSRF)          | **부활 필수** — 쓰기 라우트가 하나라도 생기면                  |
> | 본문 1MB 캡 · 청크 경계 UTF-8     | **부활 필수** — 이번엔 신뢰할 수 없는 클라이언트가 붙는다      |
> | 경로 traversal 403                | 조건부 — 정적 파일을 서빙하면 필요, 화이트리스트만 쓰면 불필요 |
> | 정적 서빙·SPA 폴백·캐시 헤더·gzip | 모바일 뷰에 자체 번들을 서빙하면 **부활**                      |
>
> **`web/test/serve.test.ts` 는 지웠지만 git 히스토리에 있다**(`f94e5e4` 이전). 5단계 착수 시 그 파일을 **명세로 다시 꺼내 읽을 것** — 이미 한 번 검증된 방어 목록이고, 여기서 처음부터 다시 생각하면 그때 물었던 것을 다시 문다(L-12·L-13·감사 ①#45).

**BroadcastChannel** 은 **다른 프로세스라 도달 불가** — 라이브 갱신이 필요하면 SSE/WS 로 **별도 메커니즘**. `sync.ts` 를 "전송계층 추상화(local BC | server SSE)"로 리팩터하는 항목. (4-F 에서 BroadcastChannel 을 **안 지운** 것이 여기서 값을 한다 — 추상화할 대상이 남아 있다.)

#### 5단계-0 — 착수 전 실측과 결정 (v5 · 2026-07-19)

**5-0-1. ⚠ v4 정정 — "폰이 PC 의 SQLite 를 직접 읽으므로 정본 하나, 동기화 없음"이 성립하지 않는다.**

**5-0-2. ⚠ v4 정정 — "4단계의 순수/IO 분리가 착수 비용을 크게 낮춘다"는 곁가지에만 맞다.**

#### 5단계-A — 최소 스모크 서버 (완료 · 2026-07-19)

#### 5단계-B — 앱 데이터 읽기 전용 라우트 (완료 · 2026-07-19)

**핵심 결정 — Rust 에 도메인 로직을 두지 않는다.**
`GET /api/state` 는 `web/src/lib/db/sqlite.ts:98-130` 의 `readRows()` 를 **쿼리까지 그대로** 옮겨 **행 표현(`DbRows`)** 을 그대로 내보낸다. `AppState` 로의 변환은 폰이 이미 순수·테스트된 `db/rows.ts` 의 `rowsToState()` 로 한다.

> 매퍼를 Rust 로 다시 짜는 선택지를 탈락시켰다. 그러면 PC 경로와 폰 경로가 **서로 다른 매퍼**를 갖게 되고, 둘이 갈리는 순간 "폰에서만 값이 다르다"가 된다 — 4단계가 반복적으로 물린 "에러 없이 잘못 동작"의 가장 진단하기 어려운 형태다. 이 결정으로 Rust 쪽은 SQL 만 알게 되어 `sqlite.ts` 가 스스로에게 건 규약("로직 없음")과 같은 규약을 따른다.

- **읽기 전용 풀**(`connect_ro`) — `read_only(true)` 는 "쓰기 라우트를 안 만든다"와 **겹치는 방어**다. 겹치게 둔 이유는 5-C 가 라우트를 늘릴 때 실수로 쓰기를 열어도 SQLite 가 거부하기 때문 — 방어를 사람의 기억에 맡기지 않는다.
- **`create_if_missing` 을 켜지 않는다.** 경로가 틀리면 빈 DB 를 새로 만들어 폰에 "데이터 없음"을 보여주는데, 그건 에러 없이 잘못 동작하는 전형이다. DB 가 아직 없으면 서버는 뜨되 데이터 라우트가 **503**(빈 200 이 아니라 — 규율 11-3).
- **`docs` 테이블도 함께 내보낸다**(4단계-J). 없으면 폰에서 읽을거리·진로 지도가 빈 껍데기가 된다 — `db.rs:73-74` 가 "5단계 때문에 지금 갚는다"고 예고한 그 이유가 여기서 회수됐다.
- **`sqlx` 를 0.8 로 고정**해 `tauri-plugin-sql` 과 **같은 sqlx 를 공유**한다(둘로 갈리면 링크 부피가 두 배).

**설계가 예측 못 했고 만들다 나온 것 1건**

- **풀 생성은 async 라 런타임 안에서만 되는데, 그러면 실패가 로그로만 흐른다** — 5-A 에서 바인딩으로 한 번 물린 형태 그대로다. → `std::sync::mpsc` 로 **준비 결과를 동기 회수**(10초 타임아웃)한다. 커맨드 스레드에서 `block_on` 을 쓰지 않은 이유는 Tauri 가 그 스레드에 런타임 컨텍스트를 걸어 두면 중첩 런타임으로 패닉하기 때문.

**▶ 결정 1 의 유일한 실질 위험(`database is locked`)이 실측으로 해소됐다.**
트랙 B `5단계-B` 케이스가 **앱이 DB 를 쥔 채 쓰기를 수행한 직후** 서버의 읽기 전용 풀로 같은 값을 읽어 온다. 잠금 오류 없이 통과했다 — WAL(§5-0-4)이 실제로 읽기와 쓰기를 갈라 준다는 관측이고, "두 번째 풀"이라는 구조적 우려가 여기서 닫혔다.

**게이트 전부 녹색** — `cargo fmt`·`clippy -D warnings`·`cargo test` 61 · `verify` 86파일 855테스트 · `build` · **트랙 A 66 / 스냅샷 59장 무변경** · `tauri build`(NSIS) · **트랙 B 15 passed**(신규 1).

- `cargo test` 통합 케이스는 **`db.rs` v1·v2 스키마를 그대로 만든 임시 DB** 로 `/api/state` 의 모양을 검증한다: `present` 파싱 · 값이 **레코드 통째 JSON 문자열**로 유지되는가 · **빈 버킷이 키로 존재**하는가(`rituals`·`backlog` — 없으면 `rows.ts` 에서 undefined 가 되어 "빈 슬라이스"와 "모르는 슬라이스"가 뒤섞인다) · `ORDER BY slice, ord` 가 삽입 순서를 이기는가 · `docs` 왕복.

빌드된 exe 를 띄우고 설정에서 서버를 켠 뒤, **실제 폰 브라우저**로 안내된 주소에 접속해 스모크 화면이 뜨는 것을 확인했다. 이로써 5단계의 전송 경로가 **끝에서 끝까지** 관측됐다.

> 이 확인을 별도 항목으로 둔 이유(규율 11-1): 트랙 B 가 증명한 것은 "루프백 밖 소켓으로 열렸고 데이터가 나온다"까지였다. 실제 폰↔PC 도달은 **공유기 AP 격리 · Windows 방화벽 프로필(공용/개인) · 2.4/5GHz 대역 분리** 라는 별개 변수에 걸리고, 그건 **코드로도 트랙 B 로도 확인할 수 없다**. 여기서 막혔다면 5-C 의 번들 작업이 전부 미검증 상태로 쌓였을 것이다.

#### 5단계 재범위 (v6 · 2026-07-19) — **정본을 Rust 로, 클라이언트를 둘로**

> **사용자 결정.** 5단계는 "LAN 읽기 전용 뷰"로 출발했는데, 폰에서 **할일을 편집**하고 싶다는 요구가 나왔다. 그 요구는 읽기 전용 전제 위에 서 있는 이 단계 전체와 충돌한다 — 그래서 전제를 바꾸기로 했다.

**왜 "폰이 DB 를 직접 쓴다"가 아닌가.** `sqlite.ts:133-139` 의 증분 쓰기는 `_last` 기준선을 들고 "달라진 행만" 반영하는데, 이 기준선은 **PC 가 유일한 writer 라는 전제** 위에 있다. 폰이 몰래 행을 추가하면 PC 의 다음 편집에서 diff 가 그 행을 "사라진 행"으로 보고 **지운다.** 에러 없이 폰에서 적은 것만 없어지는 형태 — §8 이 지목한 지배적 실패 모드 그대로다.

**탈락시킨 대안과 이유.** 일반적인 다기기 편집은 ⓐ 서버 정본(Todoist·Notion) ⓑ 변경 로그 + 툼스톤 동기화 ⓒ CRDT ⓓ 단일 writer + 명령 전달 중 하나다. ⓑⓒ 는 **오프라인 동시 편집 병합**을 푸는 장치인데, **폰은 PC 가 켜져 있고 같은 망에 있을 때만 접속된다** — 그 문제가 발생할 창 자체가 없다. 없는 병에 약을 쓰는 셈이라 탈락. ⓓ(의도 전송)도 충분히 동작하고 규모가 작지만, **폰 기능이 늘 때마다 명령 종류별 배선이 붙는다.** 사용자가 정석 구조를 택했다.

**채택 — ⓐ 의 변형: 정본을 Rust 가 소유하고, 클라이언트가 둘.**

```
PC WebView ──IPC(Tauri 커맨드)──┐
                               ├──▶ Rust(정본: 매퍼 + 기준선 + 유일한 writer) ──▶ SQLite
폰        ──HTTP(토큰)─────────┘
```

> ⚠ **PC 의 저장이 HTTP 를 타게 하면 안 된다.** 그러면 포트가 점유됐을 때 **앱이 저장 자체를 못 하고**, 서버가 항상 떠 있어야 하므로 **5-A 의 "기본 OFF"가 무너진다**(3커밋 전에 근거를 달아 정한 보안 결정이 뒤집힌다). PC 는 IPC 로 붙어 포트 없이 저장하고, HTTP 는 **폰이 들어오는 문**으로만 남는다.

**얻는 것**: writer 가 하나로 유지돼 기준선 문제가 원천적으로 없다 · 두 클라이언트가 **같은 쓰기 경로**를 타므로 "폰에서만 다르다"가 생길 수 없다 · 프런트가 SQL 을 안 쓰게 되어 capabilities 에서 `sql:allow-execute` 를 뺄 수 있다(5-E).

> ## ⚠ v7 (2026-07-19) — **아래 단계 분할(5-D~5-H)은 폐기됐다.** v6 은 "집 안에서만 편집"을 전제로 정본을 **Tauri 바이너리 안** Rust 에 두는 계획이었는데, 사용자가 **"어디서나 편집"** 을 택하면서 정본이 Tauri 밖으로 나가야 한다. 아래 §5단계 재범위 v7 이 대체 계획이다.

> **살아남는 것**: 위의 "왜 폰이 DB 를 직접 쓰면 안 되는가"(기준선 손상) · 5-C 매퍼 이식 · 행 표현 유선 계약. **폐기되는 것**: 5-E(정본을 Tauri 안으로) 이후 전부.

**▶ 5-C 완료 (2026-07-19).** `src-tauri/src/rows.rs` — `state_to_rows`·`rows_to_state`·`diff_rows` 이식 + **순수 테스트 11케이스**(Tauri 런타임 없이 `cargo test`). 계획대로 **배선은 안 했다**.

**만들다 나온 것 1건 — 행 모양이 두 곳에 정의돼 있었다.**
5-B 의 `server.rs::read_rows` 가 응답 JSON 을 `json!` 리터럴로 손수 짓고 있었다. `rows.rs` 가 같은 모양을 타입으로 정의하면서 **정의가 둘**이 됐고, 이건 5-B 가 "매퍼를 Rust 로 복제하지 않는다"고 정한 것과 같은 종류의 divergence 다. → `read_rows` 를 **타입 기반으로 교체**했다. 5-B 의 `/api/state` 모양 검증 테스트가 **한 글자도 안 바뀐 채 통과**한 것이 등가성의 증거다.

> ⚠ 트랙 B 에서 `IPC 왕복 — workspace_status` 가 **flaky 1회**(재시도 통과). 재실행에서는 15개 전부 통과해 **재현되지 않았다.** 매퍼와 무관한 부팅 타이밍으로 보이지만 **원인은 확인 못 했다**(규율 11-1). 재발하면 그때 판다.

**⚠ 5-C 착수 시 주의 — `serde_json` 의 키 순서.**
`stateToRows` 는 `Object.entries(state)` 순회 순서를 `present` 배열에 그대로 싣고, 그 배열은 `meta` 에 **JSON 문자열로** 저장된다. Rust 의 `serde_json::Map` 은 기본이 `BTreeMap`(사전순)이라 **순서가 달라지면 diff 가 매번 "변경됨"으로 판정**해 쓸데없는 쓰기가 계속 난다. → `serde_json` 에 **`preserve_order` 피처**를 켠다. 이건 조용히 잘못 동작하는 부류라 5-D 대조가 잡아 주기 전에 미리 못박는다.

D1 이 **SQLite** 라 `rows.rs` 의 행 모델이 거의 그대로 간다. 무료 티어가 넉넉하고 **안 잠든다**(Render·Supabase 무료 티어는 놀면 잠들어 "항상 켜진 호스트"와 정면으로 안 맞는다). ⚠ 무료 티어 조건은 이 문서 작성 시점 기준이고 **가입 전 현재 조건을 확인해야 한다**.

**동기화 비용 정정 — CRDT 는 필요 없다.**
v6 은 "어디서나 편집이면 진짜 동기화 엔진이 필요하다"고 적었다. 절반만 맞다. CRDT 는 **여러 명이 같은 텍스트를 동시에** 고칠 때 필요한 물건이고, **단일 사용자**(N4)는 같은 할일을 두 기기에서 같은 순간 고칠 일이 사실상 없다. → **레코드별 `updated_at` + 툼스톤 + last-write-wins** 로 충분하다.

> ⚠ **실제 청구서: 지금 스키마에 그 둘이 다 없다.** `db.rs` 의 어떤 테이블에도 `updated_at` 이 없고, 삭제는 행을 **그냥 지운다**(툼스톤 없음). 툼스톤이 없으면 "이 행이 없다"와 "이 행이 지워졌다"를 구분 못 해 **삭제가 부활한다** — 폰에서 지운 할일이 PC 동기화 때 되살아나는 형태다. v6 이 "우리는 툼스톤이 필요 없다"고 한 것은 **집 안 전용 전제에서만** 참이었다.

5-D·5-E 를 앞에 둔 이유: **클라우드 계정 없이 만들 수 있고, 어느 호스트를 고르든 필요하다.** 호스트 선택을 미루면서도 진도가 나간다.

**⚠ 이 전환이 잉여로 만드는 것 — 정직하게 기록한다.**
**5-A·5-B(LAN 서버)는 폰이 클라우드에 직접 붙는 순간 존재 이유가 대부분 사라진다.** 커밋 2개 분량이다. 남길 근거는 하나 있다 — **클라우드가 죽거나 인터넷이 없을 때의 집 안 폴백**. 다만 그 값이 유지비보다 큰지는 5-H 에서 실사용을 보고 판단한다. 지금 지우지 않는 이유는 판단 근거가 아직 없어서지, 값이 증명돼서가 아니다.

**살아남는 것**: `rows.rs` 매퍼(5-C) · 행 표현 유선 계약 · 단일 writer 통찰(클라우드가 그 writer 가 된다) · 4단계가 백엔드를 Rust 로 모아 IO 를 분리해 둔 것.

**⚠ 새로 지는 책임**: 클라우드 서비스를 운영하게 되면 **배포·인증·백업이 내 몫**이다. I1(백업 호환)이 여기서 더 중요해진다 — 클라우드가 사라져도 내보내기 JSON 하나로 복구할 수 있어야 한다.

## 10. 탈락시킨 대안

- **원격 서버 + DB** — 내구성만이면 **앱이 소유한 로컬 파일**(2단계)이 더 안전하고 싸다. 그리고 원격으로 가도 **볼트는 여전히 로컬**이다(`knowledge/` 마크다운을 이 기계에서 Obsidian 으로 편집하고 `pipeline/` 파이썬이 직접 읽는다 — 동기하려면 Dropbox 를 직접 만드는 일). 네트워크 노출은 인증·세션·CSRF·TLS·백업 운영을 사용자 1명을 위해 세우게 한다.
- **Next.js/RSC** — 서버 유무와 무관하게 값이 없다: SEO 없음 · 낯선 방문자 없음 · 사용자 1명이라 SSR 이 아낄 TTFB 가 없음 · **렌더할 데이터가 서버에 없다**(소유권이 클라이언트).
- **OPFS + wa-sqlite(WASM) + Worker** — Rust 없이 SQLite·Worker 이득을 대부분 얻는 유력 후보. 탈락: 2프로세스 실행이 남고 **File System Access API 에 watch 가 없어 파일 감시가 불가능**(§4-3단계가 제품 성격 변경이라 판단한 기능).
- **Electron** — 무겁고 Node 런타임을 안고 간다.
- **SonarQube Server/Cloud** — 룰은 `eslint-plugin-sonarjs` 로 인프라 0에 얻는다(§0-F). 서버가 더 주는 건 대시보드·추세뿐이고 Cloud 는 소스가 제3자로 나간다. 추세가 필요해지면 나중에 얹어도 룰 엔진이 같아 재작업 없음.
- **전면 재작성** — N1. 고점을 내리는 유일한 경로.
- **Tailwind 를 "안 함"** — 원래 판단이었으나 **사용자 지시로 6단계 채택**. 근거 정정도 기록: 처음엔 "레이아웃 기하가 복잡해 Tailwind 가 약하다"고 했으나 실측하니 calc/clamp/grid 는 158개(2%)뿐이라 **그 논거는 틀렸다**. 실제 마찰은 관계형 셀렉터 1,904개다.

## 11. 1~4단계에서 얻은 작업 규율 (5·6단계에 그대로 적용)

> v4 신설. 위 정정 10건이 **우연히 잡힌 게 아니라** 몇 가지 습관에서 나왔다. 남은 단계에서도 같은 습관이 값을 하므로 규칙으로 승격한다.

**11-1. 예측과 관측을 구분한다.** "보장되지 않는다"(명세의 진술)와 "발화하지 않는다"(관측)는 다른 명제다. 전자를 근거로 후자를 가정하면 **검증 없이 복잡도를 산다** — 1단계에서 훅 하나를 만들었다 되돌린 값비싼 교훈이고, 4-F 의 `<a download>` 와 4-I 의 FSA 가 그 규율로 갈렸다(전자는 진짜 죽어 있었고, 후자는 멀쩡했다). **확인 못 한 것은 "확인 못 했다"고 적는다**(AnkiConnect CORS).

**11-2. 순수 함수와 IO 를 가른다.** 2단계-B(`rows`/`sqlite`)에서 시작해 4단계 전체에 적용했다. 이게 주는 것 셋: ① Tauri 런타임 없이 `cargo test` 로 검증 ② 언어 경계가 늘어도 위험이 안 늘어난다(§8 "Rust 10개 모듈"의 완화책이 *한정*이 아니라 이 분리다) ③ **5단계가 HTTP 핸들러에서 같은 함수를 재사용할 수 있다**(§4-5단계 결정 2).

**11-3. 정본을 쥔 층은 침묵하지 않는다.** 2단계-E 에서 `getDb`·`writeRows`·`dual` 이 조용히 `false` 를 돌려주는 바람에 원인을 못 찾았고, 로그를 넣자 30초 만에 나왔다. 4단계의 결함 6건 중 **5건이 "에러 없이 잘못 동작"** 이었다. → 경계 층은 실패를 **값으로든 로그로든 반드시 드러낸다**(`artifactRead` 가 `vaultScan` 과 달리 에러를 안 삼키는 이유 · `download` 가 결과를 토스트로 알리는 이유).

**11-4. "있었다"가 "옮겨야 한다"는 아니다.** 각 계약마다 **지금도 누가 읽는가**를 먼저 묻는다. 4-C 의 `stats` 6종과 4-F 의 capabilities 플래그를 그래서 안 만들었고, 안 옮긴 것들이 하필 **결함을 품고 있었다**는 게 이 규율의 근거다.

**11-5. 게이트는 단계마다 4종을 다 돌린다.** 4-F 에서 사용자 문구 18곳을 바꾸고 **트랙 A 를 안 돌려** 스냅샷 2장이 밀린 채로 넘어갔다(4-G 가 잡았다). 문구를 바꾸면 픽셀이 바뀐다는 건 자명한데도 놓쳤다 — **"이번엔 관계없다"는 판단이 가장 자주 틀린다.** ⚠ 6단계는 스타일을 통째로 바꾸므로 **feature 단위로 트랙 A 를 돌릴 것**.

**11-6. 코드에 적은 약속도 대조 목록에 넣는다.** 4-H ② 는 설계 문서가 아니라 **내가 `research.rs` 주석에 "4-F 에서 고친다"고 적어 둔 것**이었고, 설계 문서만 대조해서 빠뜨렸다. 단계 종료 시 `grep` 대상은 설계 문서 + **소스의 "다음 단계에서" 주석**이다.

**11-7. 검증이 검증 대상을 망가뜨리지 않게 한다.** 트랙 B 4-D 케이스는 잡 이력을 12칸만 보관하는 저장소에 매 실행 1건씩 쌓아 **열두 번째 실행에서 실제 기록을 전부 밀어낼** 뻔했다 → 테스트가 자기 흔적을 치운다. 같은 이유로 볼트 감시 검증은 `_index.json` 을 **같은 바이트로 다시 써서** mtime 만 건드린다.
