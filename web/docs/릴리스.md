# 릴리스 — 배포본 만들기와 **자동 업데이트 전달**

> **이 문서가 SSOT 인 것**: 서명키 취급 · 릴리스 아티팩트 · `latest.json` · 업데이트가 사용자에게 닿는 경로.
> 설계 근거는 `src-tauri/src/updater.rs` 머리주석, UI 는 `web/src/features/settings/UpdateCard.tsx`.

## 0. 왜 이게 생겼나 (2026-07-25)

같은 감사에서 **텔레메트리**(`/api/log` · 런북 §7-7)를 넣어 배포 후 결함을 _알게 되는_ 경로를 만들었다. 그런데 그 수정을 **전달할** 경로가 없었다 — 배포가 NSIS 인스톨러 수동 재설치뿐이었다.

> **관측과 전달은 짝이다.** 한쪽만 있으면 다른 쪽이 무의미해진다: 고칠 것을 몰라도 배포 경로만 있으면 쓸 데가 없고, **결함을 알게 됐는데 전달할 방법이 없으면 관측이 좌절만 만든다.** 종전이 후자였다.

---

## 1. ⚠⚠ 서명키 — 이 문서에서 가장 중요한 절

업데이트는 **서명된 것만** 설치된다. 공개키는 `src-tauri/tauri.conf.json` 의 `plugins.updater.pubkey` 에 박혀 배포본마다 고정되고, 개인키로 서명하지 않은 업데이트는 클라이언트가 **거부**한다.

| 파일                         | 무엇       | 취급                                                                             |
| ---------------------------- | ---------- | -------------------------------------------------------------------------------- |
| `src-tauri/.updater-key`     | **개인키** | ⚠ 커밋 금지(`.gitignore` 의 «Tauri 업데이터 서명키» 절) · **오프라인 백업 필수** |
| `src-tauri/.updater-key.pub` | 공개키     | 커밋 안 하지만 비밀 아님(값은 `tauri.conf.json` 에 이미 들어감)                  |

**두 방향으로 모두 위험하다 — 어느 쪽도 나중에 복구할 수 없다:**

- **유출되면**: 이 앱의 업데이트를 **사칭**할 수 있다. 사용자 PC 에서 임의 코드가 도는 것과 같다. CI 의 `secret-scan` 잡(gitleaks · 전 이력 스캔)이 뒤늦게 잡지만, push 된 시점에 이미 유출이다.
- **잃어버리면**: 이 앱에 **다시는 업데이트를 배포할 수 없다.** 새 키로 서명한 업데이트는 기존 사용자가 거부한다. 남는 길은 새 공개키를 박은 빌드를 만들어 **손으로 재설치시키는 것**뿐이다.

> ✅ **지금 해야 할 일 하나**: `src-tauri/.updater-key` 를 이 저장소 **밖**(비밀번호 관리자 · 오프라인 저장소)에 백업하세요. 이 파일은 재생성할 수 없습니다.

키를 처음부터 다시 만들어야 한다면(유출 등):

```bash
npx tauri signer generate -w src-tauri/.updater-key
# 출력된 공개키를 src-tauri/tauri.conf.json 의 plugins.updater.pubkey 에 붙여넣는다.
# ⚠ 이 시점에 기존 배포본은 앞으로의 업데이트를 전부 거부한다 — 사용자 재설치가 필요하다.
```

## 2. 릴리스 절차

### 2-1. 버전 올리기 — **두 곳이 같아야 한다**

```
src-tauri/tauri.conf.json   "version": "0.2.0"
src-tauri/Cargo.toml        version = "0.2.0"
```

⚠ 업데이터는 **`tauri.conf.json` 의 버전**을 현재 버전으로 보고 `latest.json` 의 값과 비교한다. 둘이 어긋나면 "새 버전이 있다"고 잘못 말하거나 반대로 침묵한다.

### 2-2. 게이트 통과 후 서명 빌드

```bash
# 게이트가 먼저다 — 단계 목록의 정본은 `web/scripts/gate.mjs` 의 `ALL` 배열이다
# (CLAUDE.md 의 게이트 절은 요약이고, 스스로 정본이 아니라고 적는다 · 2026-08-06 순환 정정)
cd web && npm run gate && cd ..

# 서명 빌드. 환경변수 두 개가 서명을 켠다(없으면 서명 없이 나가고 업데이트가 안 붙는다).
export TAURI_SIGNING_PRIVATE_KEY="$(cat src-tauri/.updater-key)"
export TAURI_SIGNING_PRIVATE_KEY_PASSWORD=""      # 키 생성 시 비밀번호를 안 걸었으면 빈 문자열
npm run tauri:build
```

⚠⚠ **순서가 계약이다 — 게이트를 서명 빌드 «뒤»에 돌리지 마라**(2026-08-31 실사고). 게이트의
`ALL` 안에 **`tauri:build` 단계가 있다.** 그래서 서명 빌드를 먼저 하고 게이트를 나중에 돌리면
게이트가 인스톨러를 **서명 없이 다시 만들어** 디스크의 `.exe`·`.sig` 를 갈아엎는다 — 매니페스트에
적어 둔 서명이 고아가 되고 `release:verify` 의 「서명 ↔ 로컬 .sig」가 어긋난다(그날 실제로 그랬다).
위 순서(게이트 → 서명 빌드 → 매니페스트 → 배포)를 지키면 셋이 **한 빌드에서** 나온다.

⚠ **`.sig` 도 `release-assets/` 에 넣어라.** `.exe` 만 넣으면 그 대조가 실패가 아니라 **「생략」**
으로 조용히 지나간다(_"서명 대조 생략(release-assets 에 … .sig 없음)"_) — 배포는 초록으로 끝나는데
정작 가장 중요한 검사가 안 돈 상태다.

⚠ **`tauri:build:fast`(`--no-bundle`)를 쓰지 말 것.** 그건 개발 루프용이고 인스톨러·업데이트 아티팩트를 안 만든다(루트 `package.json` 의 `_주석:build:fast`).

산출물(`src-tauri/target/release/bundle/nsis/`):

| 파일                               | 무엇                                                |
| ---------------------------------- | --------------------------------------------------- |
| `러닝허브_0.2.0_x64-setup.exe`     | 신규 설치용 인스톨러                                |
| `러닝허브_0.2.0_x64-setup.exe.sig` | **서명** — `createUpdaterArtifacts: true` 가 만든다 |

⚠ `.sig` 가 없으면 서명 환경변수가 안 걸린 것이다. 그 상태로 릴리스하면 **모든 클라이언트가 업데이트를 거부**한다.

### 2-3. `latest.json` 만들기

업데이터가 읽는 파일이다.

> ⚠⚠ **어디에 두는가가 2026-07-26 감사(C3)에서 바뀌었다 — 아래 2-4 를 먼저 읽을 것.** 종전엔 GitHub Releases 였는데 그 URL 은 **실측 404** 였다(저장소가 비공개 → `api.github.com` 도 404 → 업데이터는 토큰을 안 싣는다). 지금은 **사용자 자신의 Workers 오리진**이고, 앱은 그 주소를 클라우드 설정의 `baseUrl` 에서 **런타임에** 만든다(`lib/cloud/client.ts` `updateManifestUrl`). ⚠ 저장소 안의 자리는 **둘로 갈렸다**(H12 · 아래 2-4): 매니페스트만 `web/public/updates/`(추적됨 · 빌드 입력)이고 **인스톨러는 `web/release-assets/`** 다.

```json
{
  "version": "0.2.0",
  "notes": "사용자가 설치 전에 읽는 릴리스 노트. UpdateCard 가 그대로 보여 준다.",
  "pub_date": "2026-08-01T00:00:00Z",
  "platforms": {
    "windows-x86_64": {
      "signature": "<러닝허브_0.2.0_x64-setup.exe.sig 파일의 내용 전체>",
      // ⚠⚠ **실물 형태로 적는다**(O024 · 2026-08-22). 여기 GitHub Releases URL 이 예시로
      //    박혀 있었는데 그건 **실측 404 로 확인돼 이 문서 아래쪽이 스스로 기각한 주소**다
      //    (비공개 저장소라 인증을 요구하고 업데이터는 토큰을 안 싣는다). 절차서가 죽은 값을
      //    먼저 쓰게 하면, 그걸 그대로 복사한 뒤 여덟 줄 뒤의 「고쳐라」를 못 읽는 경로가 생긴다.
      //    한글 파일명은 **퍼센트 인코딩**된다(실물 매니페스트 확인).
      "url": "https://<워커>.workers.dev/updates/%EB%9F%AC%EB%8B%9D%ED%97%88%EB%B8%8C_0.2.0_x64-setup.exe"
    }
  }
}
```

⚠ `signature` 는 `.sig` **파일 경로가 아니라 내용**이다. ⚠ `notes` 는 사용자가 실제로 읽는다 — "두 번째 클릭"의 값이 여기서 나온다(무엇이 바뀌는지 모르고 누르는 설치는 자동 설치와 다르지 않다).

### 2-4. 배포 — **같은 오리진(Workers) 정적 자산** (C3 · 2026-07-26)

```bash
# ① 매니페스트는 `public/`(빌드 입력 · 추적됨), 인스톨러는 `release-assets/`(빌드 입력 아님 · gitignore)
cp latest.json web/public/updates/latest.json
cp "src-tauri/target/release/bundle/nsis/러닝허브_0.2.0_x64-setup.exe" web/release-assets/

# ② latest.json 의 url 을 같은 오리진 절대 URL 로
#    "url": "https://<워커>.workers.dev/updates/러닝허브_0.2.0_x64-setup.exe"

# ③ 배포. 빌드→스테이징은 `predeploy` 훅이 대신 돈다 — 순서가 **계약이 아니라 의존**이다.
cd server && npm run deploy && cd ..

# ④ 배포 후 도달 확인 — ⭐ **`postdeploy` 훅이 자동으로 돈다**(O011 · 2026-08-22).
#    손으로 칠 일이 없다. 단독 실행이 필요할 때만: cd web && npm run release:verify
```

> ⭐ **④ 는 2026-08-22 에 훅이 됐다**(O011). 종전엔 이 줄이 「⚠ 건너뛰지 마라」라 적혀 있었는데
> **그건 처방이 아니라 사람의 기억이었다** — C1 의 처방(«순서를 계약이 아니라 의존으로»)이
> `predeploy` 로 배포 **전** 절반에만 적용돼 있었다. 이제 `server/package.json` 의 `postdeploy`
> 가 소유한다: `npm run deploy` 가 predeploy → deploy → postdeploy 를 한 줄로 돈다.
>
> ⚠⚠ **④ 가 2026-08-06 에 생겼다 — `release:stage` 는 `dist` 까지만 본다.**
> 스테이징은 "매니페스트가 가리키는 파일이 `dist/updates/` 에 있는가"를 **배포 전에** 판정한다.
> 옳지만 거기까지다: `dist` ↔ **Cloudflare 가 실제로 내주는 것** 사이는 아무도 안 봤고, 그 구간에서
> 두 번 물렸다 — C1(폴백 HTML)과 2026-08-06(전파 지연). **증상이 똑같다**(`/updates/…exe` 가
> 1433B `text/html`). 다른 것은 시간이 고쳐 주느냐뿐이고, 사람은 그걸 손으로 재현해 구분했다.
> `release:verify` 가 그 판정을 한다: 404·5xx 는 **기다리고**, 폴백 HTML 은 **기다리지 않는다**
> (자산이 등록되지 않은 상태라 시간이 안 고친다). 크기까지 대조하는 이유는 `200 OK` 만 보면
> 폴백도 통과하기 때문이다(그게 C1 의 실측이다).

> ⚠⚠ **`npx wrangler deploy` 를 직접 치지 마라 — `predeploy` 를 건너뛴다**(C1 · 2026-08-01).
> 종전엔 이 자리에 `cd web && npm run build && npm run release:stage && cd ../server && npx wrangler deploy`
> 가 적혀 있었고, 그 순서는 **절차서에만** 살아 있었다. 2026-08-01 배포가 가운데 두 줄을 건너뛰어
> `/updates/러닝허브_0.3.0_x64-setup.exe` 가 **1433 바이트 SPA 폴백 HTML** 을 돌려줬다 —
> 매니페스트는 살아 있고 서명도 유효한데 가리키는 파일이 없어, v0.2.0 사용자는 0.3.0 을
> 제안받고 minisign 검증에 실패했다. 2026-07-25 감사가 세운 "관측↔전달" 짝의 **전달 절반이
> 무효**였던 것이다. 지금은 `server/package.json` 의 `predeploy` 가 그 두 줄을 소유하고,
> `release:stage` 가 실패하면 **배포 자체가 안 나간다**.

> ⚠⚠ **인스톨러를 `web/public/updates/` 에 두지 말 것 — 2026-07-30(H12)에 자리가 바뀌었다.**
> `web/dist` 는 소비자가 **둘**이다: wrangler `assets.directory`(서빙)와 tauri `frontendDist`
> (데스크톱 번들). `public/` 은 빌드 입력이라 dist 로 복사되므로, 거기 둔 인스톨러는 **다음
> 데스크톱 인스톨러 안에 통째로 실린다**(실측 7.16MB — dist 13MB 의 절반 이상). 그리고 그 번들을
> 다시 릴리스 자산으로 두면 **매 릴리스마다 크기가 배로** 불어난다.
> 지금은 `npm run build` 가 항상 깨끗한 dist 를 만들고(`emptyOutDir`), `release:stage` 가
> **배포 직전에만** 넣는다 — 즉 `tauri:build` 는 정의상 담을 수 없다. 되돌아가면
> `npm run budget` 축 ③(번들 오염)이 빨개진다.
>
> ⚠ `release:stage` 는 복사만 하는 게 아니라 **`latest.json` 이 가리키는 파일이 실제로 있는지와
> `signature` 가 비지 않았는지를 배포 전에** 판정한다. ④의 `release:verify` 는 이미 나간 뒤의
> 확인이다. 로컬에서 판정 가능한 사실은 로컬에서 본다.

> ⚠ 배포처를 여기로 고른 이유: 폰 웹앱을 **이미 같은 오리진에서 서빙**하고 있어(런북 §7-6) 추가 호스팅이 0 이고, 자산은 공개라 업데이터가 토큰 없이 받는다. `tauri.conf.json` 의 `endpoints` 는 **미연결 사용자용 폴백**으로만 남는다 — 실제 주소는 앱이 런타임에 만든다.
>
> ⚠ 왜 GitHub Releases 를 안 쓰나: 저장소가 비공개면 그 URL 은 인증을 요구하고 업데이터는 토큰을 싣지 않는다(2026-07-26 실측 404). 공개 릴리스 전용 저장소를 따로 두는 선택지는 남아 있지만, 그러면 호스팅이 하나 늘고 확인해야 할 곳도 하나 는다.

## 2-5. ⚠⚠ 이 배포는 **되돌릴 수 없다** — 누르기 전에 읽어라

> **이 절이 없었다**(O016 · 2026-08-22 운영 축). 이 문서 전체에 `롤백|rollback` 이 **0건**이었고,
> §2 는 순서·서명·확인만 말해서 「나갔다가 안 되면 되돌리면 되지」로 읽혔다. 그건 결함이 아니라
> **의도**인데, 그 의도가 «릴리스를 누르기 전에 읽는 자리»에 적혀 있지 않았다.

**워커는 롤백된다**(런북 §7-2). **앱은 안 된다.** 세 성질이 각각 독립으로 그것을 막는다:

1. **업데이터는 전진 전용이다.** _현재 버전 < 매니페스트 버전_ 일 때만 제안한다 →
   `latest.json` 을 옛 값으로 되돌려도 **이미 올라간 사용자에겐 아무 일도 안 일어난다.**
   그들에게 도달하는 유일한 방법은 **더 높은 버전을 내는 것**이다.
2. **손으로 옛 인스톨러를 깔면 앱 대신 화면이 뜬다.** `db_version_guard` 가 `downgraded` 를
   내고 `main.tsx` 가 `DowngradeScreen` 을 그린다(C2 · **의도된 안전장치**). 즉 «옛 버전으로
   돌아가기»는 다운그레이드 차단에 정면으로 막힌다.
3. **스키마는 안 되돌아간다.** `src-tauri/migrations/` 의 `.sql` 은 sqlx 체크섬으로 불변이고,
   D1 에는 **down 마이그레이션이 없다**(복구 수단은 Time Travel 7일뿐 · 런북 §7-2).

⭐ **그러므로 되돌리기의 실제 형태는 「다음 패치를 즉시 내는 것」 하나다.** 배포 전 확인은 그
대가에 비례해야 한다:

- ① `npm run gate`(full) — `verify` 녹색은 완료가 아니다(SCA·a11y·시각회귀·실물 왕복이 그 밖).
- ② 마이그레이션이 포함되면 `src-tauri/migrations/README.md` 의 Expand/Migrate/Contract 표를
  **다시 읽는다**. 제거는 앱→DB 순서이고, 그 순서를 어기면 되돌릴 수 없는 쪽이 먼저 나간다.
- ③ 릴리스 노트(`latest.json` 의 `notes`)에 **«되돌릴 수 없는 변경»이 포함됐는지** 적는다 —
  사용자가 설치 전에 읽는 유일한 문장이다(§2-3).

## 3. 사용자에게 닿는 경로

설정 → **앱 업데이트** → `업데이트 확인` → (있으면 버전·릴리스 노트 표시) → `내려받아 설치하고 재시작`.

⚠ **부팅 시 자동 확인을 하지 않는다.** 배지로 재촉하지 않고, 자동으로 받지도 설치하지도 않는다. 근거는 `updater.rs` 머리주석 — 이 앱은 학습 세션 중에 켜져 있고, 진행 중인 집중 타이머·미저장 3문장 요약이 있는 상태의 자동 재시작이 이 앱에서 가장 나쁜 실패다.

## 4. CI 에서 서명하려면 (선택)

지금은 릴리스를 **로컬에서** 낸다. CI 로 옮기려면 시크릿 두 개를 등록한다:

| 시크릿                               | 값                                 |
| ------------------------------------ | ---------------------------------- |
| `TAURI_SIGNING_PRIVATE_KEY`          | `src-tauri/.updater-key` 파일 내용 |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | 키 비밀번호(안 걸었으면 빈 문자열) |

⚠ 그렇게 하면 **개인키가 GitHub 에 산다.** 저장소·조직이 침해되면 서명 능력이 함께 간다. 1인 프로젝트에서 로컬 릴리스가 몇 분 걸리는 것과 비교해 이 위험이 값을 하는지 먼저 판단할 것 — 지금은 **일부러 로컬**이다.

### 4-1. ⚠⚠ **CI 녹색은 「업데이트를 낼 수 있다」를 뜻하지 않는다** (V037 · 2026-08-22)

CI 의 `shell-build` 는 매 실행마다 **버리는 일회용 키**를 만들어 서명한다. 그 스텝이 통과하는
것은 «번들(NSIS)·서명 **경로**가 돈다»는 뜻이지 «이 산출물을 사용자가 받는다»가 아니다 —
배포본에 구워진 `pubkey` 와 짝이 아닌 키라 **런타임에 수락되지 않는다.** 그건 결함이 아니라
**안전장치**다(CI 산출물이 진짜 업데이트로 위장할 수 없다는 뜻이고, CI 는 인스톨러를 업로드도
하지 않는다).

**문제는 그 사실이 `ci.yml` 주석에만 있었다는 것이다.** 릴리스를 내는 사람이 여는 문서는
여기인데, 여기엔 한 글자도 없어서 «CI 가 서명 빌드를 통과했으니 서명은 괜찮다»로 읽힐 수 있었다.

⭐ **그 축을 실제로 판정하는 것은 `npm run release:verify` 다**(O001 · 2026-08-22). 그 검사기가
`tauri.conf.json` 의 `pubkey` 에서 key id 를 뽑아 매니페스트 서명의 key id 와 대조한다 —
**둘이 다르면 배포 전에 죽는다.** 그게 없던 동안의 실패 형태는 이랬다:

> 키를 재생성했거나 다른 기기/옛 백업의 키를 썼다 → `tauri:build` 통과(**어떤 유효한 minisign
> 키로도 서명된다**) → `release:stage` 통과 → `release:verify` 통과(로컬 `.sig` 와 서빙 값이
> 같다 — **둘 다 같은 잘못된 키에서 나왔으므로**) → 그런데 **전 사용자가 검증 실패**.
> 그리고 이 앱은 부팅 시 자동 확인을 안 하므로(§3) **사용자가 설정에서 누르기 전까지 아무도
> 모른다.**
