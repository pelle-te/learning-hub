# 클라우드 전환 설계 v1 — 여러 기기에서 보고, 편집한다

> **트리거**(2026-07-19): 사용자가 폰에서 **할일을 편집**하고 싶다고 했고, 이어서 _"근본이 꽤 많이 변경됐잖아? 여러 기기에서 접속하면서 편집까지 할 수 있게 구현하려던 거니까 이거에 맞춰 대대적으로 재설계해야 하지 않아?"_ 라고 물었다. 옳은 물음이었다.
>
> **이 문서가 `플랫폼개편-설계.md` 를 대체한다.** 저 문서는 **지우지 않는다** — 0~5단계 결정 근거, 특히 "실행이 뒤집은 진술 10건"과 §11 작업 규율 7가지가 거기 있고, 그건 이 문서가 **승계할 자산**이다. 다만 저 문서는 v1→v7 로 다섯 번 개정되며 **폐기된 층과 살아있는 층이 뒤섞여** 더는 설계서로 기능하지 않는다(§10 이 "원격 서버 탈락"이라 적은 채로 v7 이 원격 서버를 채택했다). 그래서 새로 쓴다.
>
> **수치는 전부 실측**이며 출처를 파일:줄로 남긴다. 근거는 2026-07-19 의 6렌즈 전수 감사다(§2).

## 0. 한 문단 요약

러닝허브는 **로컬 자원에 깊이 묶인 데스크톱 앱**이다 — 볼트 파일, 파이썬 도구, Ollama, Anki. 그런데 사용자가 폰에서 편집하고 싶은 것은 그중 **아무것도 아니고**, `AppState`(계획·할일·완료·일정) 하나다. 그래서 앱을 통째로 옮기지 않는다. **앱 데이터만 클라우드로 올리고, 로컬 자원은 PC 에 남긴다.** 이관 대상은 실측 **약 800KB** 이며, 진짜 비용은 용량이 아니라 **인증·입력검증·오프라인 큐**에 있다.

## 1. 목표 · 비목표

### 1-1. 목표 (G)

- **G1.** 폰에서 **캘린더(일/주) 조회 + 할일 편집**이 된다. PC 가 꺼져 있어도.
- **G2.** PC 와 폰의 편집이 **서로 덮어쓰지 않는다.** 특히 **삭제가 부활하지 않는다.**
- **G3.** 로컬 자원 기능(볼트·파이썬·AI·Anki)은 **하나도 잃지 않는다.**
- **G4.** 클라우드가 사라져도 **내보내기 JSON 하나로 복구**된다(I1 승계).

### 1-2. 비목표 (N)

- **N1. `features/` 재작성 금지.** 실측 17,149줄. 스케줄러 엔진·간격반복·일편집기 좌표·학위요건에 수년치 디버깅이 박혀 있다. **갈아엎기가 고점을 내리는 유일한 경로.** — 이전 문서에서 승계, 무변경.
- **N2. 프런트 프레임워크 교체 금지.** React 19 + Vite + zustand. ⚠ **근거를 갱신했다** — §5-1 참조. 이전 근거 4개 중 하나("렌더할 데이터가 서버에 없다")가 이 전환으로 **거짓이 됐고**, 틀린 근거를 남겨 두면 다음 세션이 그걸 빌미로 전체를 다시 연다.
- **N3. Python 파이프라인 재작성 금지.** 실측으로 재확인: `pipeline/pyproject.toml:28` 이 `dependencies = []` — 핵심 경로가 stdlib only 다. 건드릴 이유가 없다.
- **N4 (재정의).** ~~"다중 사용자·인증은 범위 밖"~~ → **"다중 *사용자*는 범위 밖. 단일 사용자의 *다중 기기*는 범위 안이고, 그에 필요한 인증은 세운다."**
  > ⚠ 이 재정의가 **필수**다. 옛 N4 를 문자 그대로 읽으면 **N4 가 클라우드 단계를 금지한다.** 이전 문서는 v7 에서 클라우드를 채택하고도 N4 를 안 고쳐 자기모순 상태로 남았다(감사 지적).
- **N5 (신설). 볼트·교재를 클라우드로 옮기지 않는다.** 근거는 §3-2 실측.

## 2. 실측 (2026-07-19 · 6렌즈 전수 감사)

### 2-1. 용량은 제약이 아니다

| 자원                         | 크기          | 클라우드 대상                  |
| ---------------------------- | ------------- | ------------------------------ |
| 앱 SQLite(`learning-hub.db`) | **106 KB**    | ✅ 정본                        |
| 산출물 8종(실재 6종)         | **약 300 KB** | ✅ 읽기 전용                   |
| 볼트 인덱스 `_index.json`    | **348 KB**    | △ 폰 볼트 조회의 **최소 집합** |
| 볼트 노트 597개 본문         | 6.5 MB        | ✗                              |
| `knowledge/` 전체            | 37.7 MB       | ✗                              |
| `sources/` 교재              | **498.6 MB**  | ✗ (hub 코드 경로 **0건**)      |

> **총 이관 대상 ≈ 800KB.** 무료 티어(수 GB) 기준 반올림 오차다. 하루 1회 스냅샷을 1년 쌓아도 300MB 수준.
>
> ⚠ **이 사실이 결정 하나를 되열었다** — §9-2 참조.

### 2-2. 백엔드는 분리를 절반 이상 해뒀다

규율 11-2(순수/IO 분리)가 실제로 지켜졌다. `rows.rs` 는 `tauri` 참조가 **0회**이고, `artifact.rs:93 read_at(&Path)` · `anki_scan.rs:98 scan_at(&Path)` · `server.rs:368 start_with(...)` 가 이미 인자 주입형이다. Tauri 플러그인 결합은 4곳뿐이며 그중 `dialog` 는 **Rust 코드가 한 줄도 안 쓴다**(`lib.rs:51` 등록뿐).

**남은 벽 3가지** — 성격이 다르다:

| 벽                                                           | 성격                                                                                          | 비용                 |
| ------------------------------------------------------------ | --------------------------------------------------------------------------------------------- | -------------------- |
| `workspace::resolve(&AppHandle)` 가 커맨드 9개 중 6개를 관통 | **기계적** — 전부 "워크스페이스 경로 한 줄" 때문. `&Path` 주입으로 뒤집으면 6개가 즉시 풀린다 | 낮음, **가성비 1위** |
| `ollama.rs:400` Webview 채널 스트리밍                        | **국소적** — 그 위 `build()` 까지 전부 순수. 송신 sink 를 trait 으로 추상화                   | 중간                 |
| 쓰기 경로가 아직 프런트 소유                                 | **설계 선행 필요**                                                                            | 높음                 |

### 2-3. 프런트는 이미 낙관적이다 (좋은 소식)

`useApp.ts:118-124` 의 쓰기가 `void` fire-and-forget 이라 **네트워크 왕복이 끼어도 happy path 가 안 바뀐다.** 그리고 `pending` 이 immer 레시피의 **의미론적 연산 큐**이고 `onSync` 에 rebase 재적용 루프가 이미 있다 — 멀티탭용으로 만든 것이 **다기기에 그대로 일반화된다.**

작업이 한 곳에 모여 있다: **`useApp.ts:103-190`, 함수 4개 약 90줄.**

### 2-4. 슬라이스 단위 분할은 성립하지 않는다

`items` 를 5개 탭이 쓰고 사실상 전 탭이 읽는다. 스케줄러(`engine.ts` 493줄)가 `items`+`routine`+`weekAlloc`+`dayOverrides`+`events`+`completions` 를 **한 번에** 받아 파생물 `res` 를 만들고, 캘린더·오늘·통계가 전부 그걸 소비한다. 게다가 `alloc`·`items` 는 **그 파생물을 쓰기 인자로 되먹인다**(`AllocBoard.tsx:88` `setAllocCell(st, res, …)`).

프런트 감사가 독립적으로 같은 결론에 도달했다 — 부분 로딩은 `present` 배열에 **세 번째 상태("아직 안 불러옴")** 를 만드는데, 그건 "없음"과 구분되지 않아 `writeRows` 가 미로딩 슬라이스를 삭제로 보고 툼스톤을 찍는다. 그리고 `schedule()` 하나가 **22개 슬라이스를 상주 요구**한다.

> **→ 동기화 단위는 `AppState` 전체 하나다.** 잘라낼 수 있는 건 주변부 3개(`degree`·`weekly`·`retentionLog`)뿐이고 그걸 위해 복잡도를 살 이유가 없다.

### 2-5. 사용자가 원한 것은 이미 만들어져 있다

"캘린더 일/주/월 + 할일 편집"은 정확히 **`schedule` 탭**(2,015줄)이다. 세 뷰와 할일 편집이 같은 파일에 있고, **백엔드 import 가 0건**이며, 모바일 CSS 가 이 저장소에서 가장 두껍다(700px 규칙 4파일).

**폰에서 완전히 동작 가능한 탭이 11개**다: `today` `schedule` `alloc` `degree` `items` `journal` `review` `review-run` `guide` `plan-host` `routine`.

### 2-6. 데이터는 가볍지 않다

| 무엇                                                   | 민감도                        |
| ------------------------------------------------------ | ----------------------------- |
| **성적·학점·GPA**(`CourseSchema.grade`·`DegreeSchema`) | 학적부에 준함                 |
| **일정**(`PlanEventSchema` — 날짜+시각+제목+메모)      | 쌓이면 **생활 패턴 프로파일** |
| **자유 서술**(요약·주간노트·일과노트·일정메모)         | 내용을 스키마가 제약하지 않음 |
| **진로 메모·독후감**(`docs`)                           | 개인적 서술                   |

없는 것(정확히 하기 위해): 비밀번호·결제정보·주민번호·건강정보·위치좌표 — **전부 없다.**

> **정직한 판정**: 특수 카테고리 개인정보는 아니다. 그러나 **성적 + 일정 + 자유 서술 3종의 조합**은 한 개인의 학업 능력·생활 리듬·내면 고민을 상당히 정확히 재구성한다. **"학습 앱이니 별거 없다"는 판단은 틀렸다.** 비밀번호는 바꿀 수 있지만 성적 이력은 못 바꾼다.

### 2-7. 부수 실측 — AI 5종은 지금도 안 돈다

`~/.ollama` 가 **10KB**로 측정됐다. 모델이 이 기계에 설치돼 있지 않다. 즉 코치·어휘·브리핑·회고·임베딩은 **현재 동작하지 않는 상태**이고, 클라우드 이행에서 잃을 것이 없다. `OLLAMA_BASE_URL`(`ollama.rs:47`) 한 줄로 원격 추론 서버로 갈 수 있고, 프롬프트 빌더·파서는 전부 순수라 재사용된다.

## 3. 분할선

### 3-1. 클라우드로 가는 것

- **`AppState` 전량**(106KB) — 정본이 여기로 이동. 폰이 편집하는 대상.
- **`docs`**(내 요약·독후감·진로 메모) — 사용자 저작물. 정본이 따로 없다.
- **산출물 8종**(300KB) — 읽기 전용. 폰이 `goals`·`reads`·`markets` 등을 보려면 필요.
- **`_index.json`**(348KB) — 폰에서 볼트 **목록** 조회용. ⚠ 노트 본문은 안 옮긴다 — `vault_scan` 의 정본 경로가 본문을 아예 안 읽는다(subject·folder·kind·status 만).

### 3-2. PC 에 남는 것 (이관 **불가**)

| 무엇                       | 왜 원리적으로 불가한가                                                                                                                     |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| **Anki 전부**              | `anki_io.py:31` 이 `%APPDATA%/Anki2/*/collection.anki2` 를 글롭하고 `anki.rs:32` 가 `127.0.0.1:8765` 하드코딩. 원료가 사용자 머신에만 있다 |
| **볼트 파일 감시**         | 파일시스템 이벤트는 원격에 없다                                                                                                            |
| **볼트 쓰기(Obsidian)**    | 정본이 로컬 마크다운 파일                                                                                                                  |
| **파이프라인 실행**        | `knowledge/CLAUDE.md` 가 "(과목)(챕터) 돌려줘 → 단계별 격리 서브에이전트"로 규정 — **크론잡이 아니라 대화형 Claude Code 세션**이다         |
| **워크스페이스 경로 추론** | `workspace.rs:69` `current_exe()` 상향 탐색. 클라우드엔 "부모 폴더"가 없다                                                                 |

> ⚠ **추론이 3벌 있다** — Rust `workspace.rs:68-85` · `vault_const.py:46` · 수집기 2종의 `HERE.parents[2]`. 전부 명시 설정으로 바뀌어야 한다. 그리고 `hub/` 는 서브모듈이라 **hub 만 클론하면 `parents[2]` 가 어긋나고 `pipeline/` 도 없다.**

### 3-3. 판단이 갈리는 것

- **`reads-collect`·`markets-collect`** — RSS/Yahoo 수집이라 네트워크만 필요하다. **클라우드에서 도는 게 오히려 이득**(PC 가 꺼져 있어도 최신). 단 스키마가 `knowledge/_meta/contract/schemas/` 를 참조하므로(81KB, 추적됨) 그 폴더는 있어야 한다.
- **`ledger-build`** — ⚠ **조용히 열화한다.** 입력 JSON 이 없어도 예외 없이 기본값으로 진행해 **exit 0 인데 0챕터**가 나온다. 클라우드에서 돌린다면 이 실패 모드를 먼저 막아야 한다.

## 4. 아키텍처

```
        ┌──────────────── 클라우드(항상 켜짐) ────────────────┐
        │  AppState 정본 · docs · 산출물 · _index.json        │
        │  인증(기기 단위) · 입력검증(.strict()) · TLS        │
        └────────▲───────────────────────────▲───────────────┘
                 │ HTTPS                     │ HTTPS
     ┌───────────┴──────────┐      ┌─────────┴──────────┐
     │  PC 데스크톱(Tauri)  │      │   폰 웹앱(PWA)     │
     │  로컬 캐시 SQLite    │      │  로컬 캐시         │
     │  + 볼트·파이썬·AI·Anki│      │  캘린더 일/주+할일 │
     └──────────────────────┘      └────────────────────┘
```

**정본은 클라우드, 두 클라이언트는 각자 로컬 캐시를 둔다.** 로컬 캐시가 있어야 ① 오프라인에서 뜨고 ② 기존 동기 읽기 전제(§2-3)를 안 깨고 ③ 데스크톱이 인터넷 없이도 로컬 자원 기능을 유지한다(G3).

**병합**: 레코드별 `updated_at` + 툼스톤 + last-write-wins(5-D 에서 이미 스키마 완료). CRDT 는 **쓰지 않는다** — 여러 명이 같은 텍스트를 동시에 고칠 때 필요한 물건이고, 단일 사용자는 같은 레코드를 같은 순간 두 기기에서 고칠 일이 사실상 없다.

**폰 앱은 `features/` 가 아니라 `lib/` 을 재사용한다.**

> 이게 가능한 **유일한 이유가 절대규칙 #2**(`eslint-plugin-boundaries` 단방향 강제)다. `lib/` 이 React 무관으로 유지된 덕에 `rows.ts`(순수 매퍼)와 `lib/scheduler` 가 그대로 폰에서 돈다. **경계 규율에 대한 투자가 여기서 회수된다** — 기록해 둘 가치가 있다.

## 5. 프레임워크·도구 재검토 결론

전수 재평가 결과 **프레임워크 층은 전부 유지가 맞고, 근거가 오히려 강해졌다.** 청구서는 전부 **데이터·계약·검증 층**에 있다.

### 5-1. 유지 (근거와 함께)

- **React 19 + Vite SPA (N2).** 이전 문서 §10 의 Next.js 탈락 근거 4개 중 **하나만 뒤집힌다**("렌더할 데이터가 서버에 없다"). 나머지 3개(SEO 없음·낯선 방문자 없음·사용자 1명이라 TTFB 이득 없음)는 그대로다. 그리고 **새 반대 근거가 더 강하다**: `tauri.conf.json:6` 이 `frontendDist` 로 정적 파일을 물리는데, SSR/RSC 는 요청마다 HTML 을 만들 런타임을 요구한다 → 셸 안에 런타임을 또 안거나(ⓐ) 클라우드에서 HTML 을 받아오거나(ⓑ). **ⓑ는 로컬 자원 앱을 인터넷 의존으로 만든다** — 명백한 퇴행이다. ⓐ를 피하려면 프런트를 두 벌 빌드해야 한다.
- **zustand + immer.** rebase 큐가 이미 낙관적 업데이트 기계다(§2-3). TanStack Query 는 **현 역할 유지**(읽기 전용 산출물 10종, mutation 0개) — 사용자 저작 상태로 확장하면 `features/` 소비처 전량을 건드려 N1 위반.
- **`eslint-plugin-boundaries`.** §4 의 이유로 값이 더 커졌다.
- **트랙 A/B 분리 · GPU 핀 · 커버리지 래칫 · CI OS 분리.** 근거가 전부 실측이고 전제 변경에 영향받지 않는다.
- **Tauri 셸의 로컬 자원 모듈 ≈3,100줄.** §3-2 가 확정.

### 5-2. 바꿀 것

| 항목                       | 무엇을 → 무엇으로                                             | 안 하면                                                                              |
| -------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| **`pending` 큐**           | 인메모리 클로저 → **직렬화 가능한 영속 의도 로그**            | 새로고침·재시작하면 미전송 편집 증발. **오프라인 큐는 정의상 재시작을 넘겨야 한다**  |

### 5-3. 6단계 Tailwind — 순서를 바꾼다

**폰 웹앱을 Tailwind 파일럿으로 삼는다.** "6단계는 1~5와 겹치지 마라"의 실제 보호 대상은 **기존 스냅샷 59장의 churn** 인데, 폰 웹앱은 베이스라인도 CSS Modules 레거시도 픽셀 결정도 없는 **완전 그린필드**라 **한 장도 건드리지 않는다**. 그리고 §6단계가 이미 "더 작은 feature 로 규약을 먼저 굳혀라"로 전환 순서를 뒤집어 놨다 — 이건 계획 위반이 아니라 **그 지침의 가장 좋은 실행**이다.

대가: Tailwind 툴링 결정(`@theme static` · 임의값 룰 · 반픽셀 예외 · 런타임 CSS 변수 주입 예외 7곳)을 6단계가 아니라 **여기서** 확정해야 한다.

## 6. 보안 — 인터넷 노출 전 필수

> 이전 문서 §10 이 _"네트워크 노출은 인증·세션·CSRF·TLS·백업 운영을 **사용자 1명을 위해** 세우게 한다"_ 고 적었다. **그 문장은 여전히 맞다.** 사용자가 "어디서나 편집"을 명시적으로 결정했으므로 진행하되, **대가를 축소해서 적지 않는다.**

### P0 — 없으면 노출해선 안 된다

1. **TLS 전 구간.** `/api/state` 가 DB 전량을 뱉으므로 **도청 1회 = 영구 전량 유출 + 토큰 탈취**. 비용은 거의 0(관리형 호스트는 기본 제공) — **진짜 요구사항은 평문 HTTP 폴백 경로를 절대 남기지 않는 것.**
2. **토큰을 URL 에서 빼고 수명·회전·폐기를 붙일 것.** 현재 모델(`server.rs:330`)은 **만료 없는 단일 PSK 를 URL 에 실어** 나른다. LAN 온보딩 편의로는 합리적이지만 인터넷에선 **유출을 알아도 대응 수단이 "앱 재시작"뿐**이다. `history.replaceState`(`mobile/index.html:86`)는 주소창만 지우지 프록시 로그·Referer·히스토리 동기화는 못 막는다.
3. **서버 측 입력 검증.** ⚠ **`AppStateSchema` 는 런타임에서 한 번도 실행되지 않는다** — `schema.ts:117` 이 스스로 그렇게 적어 뒀다. 실제 방어는 손코딩 `validShape()` **5줄**(`persistence.ts:193-204`)이고 배열 내부는 완전 무검증이다. 로컬에선 "내 파일만 연다"라 수용 가능했지만 **클라우드는 정의상 신뢰할 수 없는 입력을 받는다.**
   > ⚠ 기존 스키마를 **그대로 쓰면 안 된다.** `ItemSchema`·`AppStateSchema` 가 `.passthrough()`(`schema.ts:33,215`)인데 이건 백업 호환(I1)용 **의도된** 선택이고, 신뢰 경계에서는 정확히 반대로 작동한다. **`.strict()` 수신 전용 파생**을 만들 것. 스키마가 이미 있어 지금이 가장 싸다.

### P1 — 노출 직후 필요

4. **주체(principal) — 최소한 기기 단위.** `authed()` 가 `bool` 을 돌려준다(`server.rs:116`). 누가 접근했는지 모르면 **폰을 잃었을 때 모든 기기를 끊는 것 외에 방법이 없다.** 이건 다중 사용자가 아니라 **단일 사용자의 여러 기기 구분**이라 N4(재정의) 안에 있다.
5. **CSP 도입** — 5-2 표 참조.
6. **인증 응답에 `Cache-Control: no-store` + CORS 명시 설정.** 후자가 중요한 이유: axum 기본값(헤더 없음)이 지금 유리하게 작동하지만 그건 **의도가 아니라 우연**이다. 호스트나 프레임워크를 바꾸면 조용히 열린다.
7. **요청 크기 상한 + 레이트 리밋.** 인증 우회 위험은 낮지만(192비트 토큰) DoS 와 무료 티어 쿼터 폭주는 실재한다. `server.rs:446` 이 쓰기 라우트가 없는데도 상한을 건 선례를 그대로 승계.

### P2 — 운영 책임

8. **백업·복구 경로 검증.** G4 는 보안 요구사항이기도 하다 — 랜섬웨어·계정 탈취·호스트 폐업이 전부 같은 복구 경로를 쓴다.
9. **접근 로그.** 4번에 의존. 침해를 **알아차릴** 수단이 현재 0이다.

### 부활하는 HTTP 방어

이전 문서 4단계-G 가 "불필요"로 닫은 13건을 인터넷 기준으로 재판정: **불필요 유지 0 · 부활 10 · 조건부 2 · 프레임워크 흡수 1.** 원표는 틀리지 않았다 — _"IPC 에서는"_ 이라고 정확히 한정했다. 다만 되살아나는 비율이 이전 문서 v4 가 예상한 "상당수"보다 **높다(사실상 전부)**. 그리고 원표에 **없던 항목이 새로 생긴다**: 인증 응답 `no-store` · CORS 명시 · TLS · 토큰 수명 관리.

### ⚠ C-1 정정 — "직렬화 불가"는 잘못 잡은 문제였다

감사가 _"`pending` 이 immer 레시피(함수)라 직렬화 불가 → 오프라인 큐의 최대 비용"_ 이라 지적했고 §5-2 가 그걸 그대로 받아 적었다. **다시 보니 전제가 틀렸다 — 레시피를 직렬화할 이유가 없다.**

`pending` 이 지금 하는 일과 오프라인 큐가 해야 할 일은 **다른 문제**다:

|         | 현재 `pending`                                                                   | 오프라인 큐                                           |
| ------- | -------------------------------------------------------------------------------- | ----------------------------------------------------- |
| 무엇    | 400ms 디바운스 **도중** 다른 탭 저장 알림이 오면, 아직 DB 에 안 간 편집을 재적용 | 인터넷이 없는 동안 쌓인 편집을 나중에 서버로 밀어올림 |
| 수명    | 수백 ms                                                                          | 시간·일 단위                                          |
| 유실 시 | 디바운스 창만큼(오늘과 동일)                                                     | **사용자 편집 전부**                                  |

**핵심: 오프라인 큐의 내용물은 "의도"가 아니라 "행"이다.** 우리는 이미 행 단위 LWW 로 병합하기로 했으므로(§4), 서버에 보낼 것은 **`updated_at` 이 찍힌 dirty 행**이지 그걸 만든 레시피가 아니다. 그리고 행은 이미 JSON 이다.

**게다가 그 큐가 이미 존재한다.** 5-D 가 넣은 `updated_at` + 툼스톤이 곧 아웃박스다:

```
밀어올릴 것 = updated_at > last_pushed_at 인 행 ∪ deleted_at > last_pushed_at 인 툼스톤
```

**별도 outbox 테이블이 필요 없다.** 로컬 SQLite 가 이미 내구성 있는 기록이고(앱이 죽어도 남는다), watermark 하나만 두면 "아직 안 보낸 것"이 유도된다. `pending` 레시피 큐는 **원래 목적 그대로 인메모리로 남긴다** — 크래시 시 유실 창은 디바운스 400ms 로 오늘과 같고, 그건 이미 수용된 계약이다.

> ⚠ **남은 진짜 위험은 시계다.** watermark 를 벽시계 `updated_at` 으로 잡으면, 기기 시계가 뒤로 점프했을 때 새 편집의 `updated_at` 이 watermark 보다 작아져 **영영 안 밀려 올라간다**(조용히). → C-1 은 **단조 증가 로컬 시퀀스**를 `updated_at` 과 **별도로** 둘지, 아니면 밀어올릴 때 `max(watermark)` 를 재계산할지를 정하는 것이 실제 설계 내용이다. LWW 비교용 타임스탬프와 "보냈나" 표시를 **같은 값으로 겸하게 하면 안 된다**는 것이 교훈이다.

**→ C-1 의 실제 범위**: watermark/시퀀스 설계 + 밀어올림 대상 질의 + 재시도·백오프 + `whenSettled()` 축소(§5-2). 레시피 직렬화는 **범위에서 빠진다.**

### 이미 완료된 것 (이전 문서 5단계에서)

- **5-C** `rows.rs` — 매퍼 Rust 이식. 서버가 어디 있든 필요하다. ✅
- **5-D** `db.rs` v3 — `updated_at` + 툼스톤. 병합의 전제조건. ✅
- **5-A·5-B** LAN 서버(`server.rs` 730줄) — ⚠ **§9-1 참조.**

## 8. 불변식 (I)

- **I1. 백업 호환.** `exportSnapshot` JSON 은 구 백업을 읽을 수 있고, 내보낸 것은 구 앱이 읽을 수 있다. **클라우드가 사라져도 이 파일 하나로 복구된다**(G4).
- **I2. 레이어 단방향.** `boundaries` error 유지. 원격 호출도 `lib/` 이 소유한다. **폰 앱이 `lib/` 을 재사용할 수 있는 유일한 근거**(§4).
- **I3. 스케줄러 산출 동형.** 42케이스가 전 단계에서 그대로 통과.
- **I4. 게이트 녹색.** verify + 트랙 A + build + 트랙 B(+ 클라우드 계약 테스트).
- **I5. 명시 지시 보존.** 결정로그의 픽셀 결정을 이행이 뒤집지 않는다.
- **I6. 픽셀 동일 계약.** 스타일 이행은 "값은 이전과 픽셀 동일"이 계약.
- **I7 (신설). 단일 writer.** 어느 시점에도 정본을 쓰는 주체는 하나다. 폰이 DB 를 직접 쓰지 않는 이유이고, 클라우드가 그 하나가 된다.
- **I8 (신설). 로컬 자원 기능은 인터넷에 의존하지 않는다.** 볼트·파이썬·AI·Anki 는 오프라인에서 동작해야 한다(G3). SSR 탈락의 근거이기도 하다(§5-1).

## 9. 열린 결정

### 9-1. `server.rs` 730줄의 존폐 — **C-4 전에 정해야 한다**

폰이 클라우드에 직접 붙으면 LAN 서버의 존재 이유가 대부분 사라진다. 남길 근거는 "클라우드 다운·인터넷 없음 시 집 안 폴백" 하나다.

> ⚠ **이전 문서는 "5-H 에서 실사용을 보고 판단"이라 미뤘는데, 그건 늦다.** 폴백을 남기면 **폰 번들이 백엔드 둘(LAN axum + 클라우드)을 상대**해야 하고 인증·전송·에러 경로가 각각 두 벌이 된다. C-6 에서 발견하면 이미 지불된 뒤다. **C-4 전에 정하면 전송 추상화를 한 번만 설계한다.**

### 9-2. ⓐ PWA 오프라인 캐시만으로 충분한가 — **실측이 되열었다**

사용자는 앞서 "PC 꺼진 상태 조회"에 **ⓑ 클라우드 스냅샷 푸시**를 골랐다. 그런데 §2-1 실측이 그 선택의 전제를 바꿨다: **폰이 필요로 하는 전량이 800KB** 라 PWA 캐시 한계(보통 수십 MB)에 한참 못 미친다.

즉 **ⓐ만으로도 생각보다 훨씬 멀리 간다** — 데이터 외부 유출 0 · 무료 · 무유지보수 · P0 3건과 §6 운영 부담 전부 불필요. 한계는 "마지막 접속 시점의 데이터"와 **"폰에서 편집할 수 없다"** 두 가지다.

> **다만 G1(폰에서 편집)이 목표인 한 ⓐ 단독으로는 부족하다.** 이건 "결정을 뒤집자"가 아니라 **"조회만으로 충분한지 한 번 더 확인할 값이 있다"** 는 실측 보고다. 편집이 정말 필요하면 ⓑ 로 간다.

### 9-3. ~~클라우드 호스트 확정~~ → **결정됨: Oracle Cloud Always Free (VM)** (사용자 결정 2026-07-19)

> 설계상 이 결정을 **C-4 가 아니라 지금** 내렸다. 이유는 사슬이 하나 있기 때문이다:
> **호스트 → 서버 언어 → 검증 스키마의 모양 → 매퍼의 정본.** C-2(경계 zod)가 여기 직접 의존해서, 모르고 시작하면 다시 짜야 한다.

**채택**: Oracle Cloud Always Free (ARM · 영구 무료). **탈락**: Cloudflare Workers+D1.

**이 결정이 정하는 것**

| 항목            | 결과                                                                                                                                    |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| **서버 언어**   | **Rust.** → `rows.rs`(5-C 이식)가 **잉여가 아니라 서버 매퍼**가 된다. `db.rs` 스키마도 그대로 간다                                      |
| **검증 스키마** | ⚠ zod 를 문자 그대로 공유할 수 없다(서버가 TS 가 아니다). **SSOT 전략이 필요하다** — 아래                                               |
| **성장 여지**   | 나중에 마음이 바뀌면 파이썬 도구·Ollama 도 올릴 수 있다(ARM 4코어/24GB). Workers 로는 불가능한 선택지                                   |
| **TLS**         | ⚠ **무료로 딸려오지 않는다.** Caddy/certbot + 도메인(또는 DDNS)을 직접 세워야 한다. P0-1 의 비용이 "거의 0"에서 **실작업**으로 올라간다 |
| **운영 책임**   | OS 패치 · 방화벽 · 인증서 갱신 · 백업이 **전부 내 몫**. Workers 였다면 없었을 상시 부담                                                 |
| **가용성 위험** | Oracle 은 **놀고 있는 Always Free 인스턴스를 회수한 이력**이 있다. → G4(내보내기 JSON 복구)의 값이 더 커진다                            |

**⚠ 검증 스키마 SSOT — 이 저장소에 이미 선례가 있다.**
`scripts/gen-artifacts.mjs` 가 부모 저장소의 JSON Schema 에서 `artifacts.gen.ts`(zod)를 **생성**하고, `verify` 의 `codegen:check` 가 드리프트를 막는다. 산출물 8종이 그 방식으로 이미 안전하다.
→ **같은 패턴을 확장한다**: JSON Schema 를 SSOT 로 두고 **TS(zod) + Rust(serde/validator) 양쪽을 생성**한다. 손으로 두 벌 쓰면 이 저장소가 이미 두 번 물린 divergence 를 세 번째로 사는 것이다.

⚠ **무료 티어 조건과 가입 절차는 이 문서 작성 시점 기준이다. 가입 직전 현재 조건을 직접 확인할 것.**

### 9-4. 폰 앱 형태 — 별도 경량 웹앱으로 유지할 것인가

사용자는 앞서 **별도 경량 번들**을 골랐다. 그런데 §2-5 실측이 근거를 약화시켰다 — **`schedule` 탭이 이미 요청 그대로이고 백엔드 의존이 0**이다.

|             | 별도 번들            | `schedule` 탭 재사용   |
| ----------- | -------------------- | ---------------------- |
| 번들 크기   | 작다                 | 393.9KB gzip 예산 전체 |
| 유지보수    | **표시 로직 이원화** | 하나                   |
| 검증된 로직 | 폰용으로 다시 짬     | 그대로                 |

> 절충안이 있다: **별도 진입점 + `lib/` 재사용 + `features/schedule` 의 하위 컴포넌트만 선별 재사용.** N1 을 지키면서 번들도 작게 유지한다. C-6 착수 시 결정.
