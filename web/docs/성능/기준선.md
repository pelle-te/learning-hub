# 성능 기준선 — 러닝허브

**이 파일의 목적 하나**: 다음 회차가 «빨라졌다/느려졌다»를 **느낌이 아니라 델타로** 말하게 하는 것.
`/리뷰 성능` 1회차(2026-08-27)가 만들었다 — 그전까지 이 디렉터리는 **없었고**, 그래서 부팅 웨이브를
재는 코드가 둘이나 있는데도(`e2e-shell/shell.spec.ts` · `e2e/phone.spec.ts`) 그 수는 `console.log`
로 증발했다(`P033`).

## ⚠ 이 파일에 원시 트레이스를 넣지 마라

저장소 이력 예산이 **657 / 700 MiB(94%) · 잔여 43 MiB** 이고 증가의 86%가 e2e 스냅샷이다(`P032`).
1회차가 뽑은 DevTools 트레이스 둘은 **21.5 MB** 였고, 그대로 커밋했으면 잔여의 절반을 그 자리에서
썼다 — **지웠다.** 여기는 **요약 수치만** 든다. 재생성 방법은 각 표의 「재는 법」에 있다.

## ⚠ 수를 읽기 전에 조건을 읽어라

| 라벨                 | 무엇                                  | 조건                                                          |
| -------------------- | ------------------------------------- | ------------------------------------------------------------- |
| **실물(셸)**         | 트랙 B · 실 WebView2 + 실 SQLite      | 격리 데이터 폴더(빈 DB) · 1440×900 · OS 캐시 웜 · 16코어 머신 |
| **프록시(브라우저)** | Chromium + `vite preview`             | **SQLite 없음**(localStorage 백엔드) · GPU 없음 · 1440×900    |
| **프록시(폰)**       | Chromium 모바일 에뮬 + `vite preview` | 실물은 Cloudflare Workers 오리진 · 390×844                    |

프록시에서 잰 **절대 지연**은 실물로 그대로 옮기지 마라. **상대 비교**(A vs B)와 **JS 처리 시간**만
이관 가능하다.

## 1. 앱 실행 → 첫 데이터 (실물 · n=3 · 2026-08-27)

| 구간                                                                  | 중앙    | 범위     |
| --------------------------------------------------------------------- | ------- | -------- |
| spawn → `performance.timeOrigin` (네이티브 기동 + WebView2 문서 시작) | **508** | 463~938  |
| timeOrigin → `hub:entry`                                              | 71      | 63~110   |
| `hub:entry` → `hub:app`                                               | 196     | 170~221  |
| `hub:app` → `hub:first-data`                                          | 42      | 39~46    |
| timeOrigin → FCP                                                      | 408     | 368~476  |
| **총 spawn → first-data**                                             | **881** | 743~1243 |

⭐ **총합의 58%가 웹 층 밖이다** — `lib/perf.ts` 의 마크 셋도 번들 예산의 어느 축도 그 구간을 안 본다(`P035`).

**재는 법** `npm run e2e:shell` → `기준선.json` 의 `shell-boot.nativeToOrigin`. 트랙 B 가 `boot.rs` 의 프로세스
기동 스탬프(`boot_process_start_ms`)로 매번 잰다(P035 · 상설). ⚠ 위 표의 508 은 **`spawn()` 기준**(08-27 · 1회차가
임시 spec 으로 쟀다)이라 프로세스 생성분만큼 크다 — json 의 220(09-02)을 «508→220 개선»으로 읽지 마라, 조건이
다르다. CDP 폴링은 **50 ms** 로 — 하네스 기본 400 ms 는 양자화 오차가 크다.

**회차 간 보존** — `web/docs/성능/기준선.json`(`e2e/_perfBaseline.ts` · P033). 키는 `shell-boot.{nativeToOrigin,
entryToApp, gap, total}` · `phone-boot.bootMs`. 판정은 **계단**(이전 × 1.5 + 20 ms · 같은 `host` 만)이고 절대 임계는
없다. ⚠ 계단이면 파일을 **안 올린다**(V099 · 2026-09-02 — 종전엔 판정 전에 덮어써서 재실행 한 번에 가드가
풀렸다). 기준선을 일부러 새로 세우려면 `PERF_BASELINE_WRITE=1`. 이 파일은 e2e 가 돌 때마다 값이 바뀌므로
커밋 위생(절대규칙 #5)에서 «내 변경인가»를 보고 담는다.
