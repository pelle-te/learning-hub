# 결정 로그 (ADR) — web

> "왜 이렇게?"의 근거를 한 곳에. 코드 주석·메모리에 흩어진 결정을 승격. 새 큰 결정이 생기면 항목 추가(날짜·결정·이유·대안).

## 전수 감사 — 동기화 코어 잠복 결함 6종 (2026-07-24)

> `/감사` 6렌즈 팬아웃(web-reviewer×2·web-improver + 메인의 `server`·`src-tauri` 직독)이 잡은 결함. 전부 **정적 검사·기존 테스트 전량 녹색**이었고 대부분 무증상이라, 테스트가 아니면 못 잡는 부류다(이 저장소가 반복해 물린 "전량 녹색인데 실물에서 죽는" 계열).

- **C1 · 이관 사용자의 첫 클라우드 연결이 영구 차단됐다(무증상 · Critical).** `writeRows` 가 `diffRows(_last, rows, nextStamp())` 로 diff 전체에 **스탬프 하나**를 찍는데, 최초 localStorage→SQLite 이관은 `_last=null` 이라 **수개월치 행이 전부 같은 스탬프**를 받는다. 그 그룹이 `MAX_BATCH_ITEMS`(500)를 넘으면 `capBatch` 가 "그룹은 스탬프 경계에서만 쪼갠다"(정확성>상한)는 규칙 때문에 통째로 내보내는데, 그 초과 배치가 `schema.ts` 상한에 걸려 `push` 가 `blocked` → 워터마크 불변 → 매 회차 재차단. **그 기기는 이후 아무것도 못 올린다.** → 이관 전용 `chunkedStamp(400)` 를 `diffRows` 에 넘겨 청크마다 스탬프를 갈라 그룹을 상한 아래로 유지한다(일반 flush 는 상수 스탬프라 **한 글자도 무변경** — "한 flush = 한 스탬프 그룹" 유지). **왜 안 드러났나**: 기존 `capBatch`·`cloudSchema` 테스트가 **서로 다른 스탬프만** 써서 단일 >500 그룹을 아무도 안 만들었다 → 회귀를 `cloudOutbox.test.ts` 에 박았다.
- **H1 · 폰이 받아온 독후감·산출물을 재시작까지 못 봤다.** `docs` 의 메모리 사본 `_cache` 는 부팅(`initDocs`)에만 채워지는 **네 번째 데이터 사본**인데, `merge.ts` 머리주석은 사본 셋(SQLite·`_last`·zustand)만 다루고 이걸 빠뜨렸다. pull 이 `docs` 를 SQLite 에 병합해도 `_cache` 는 낡은 채라 `ReadsView`(`readMirrored`→`docGet`)가 빈 화면 → C-6("폰에서 읽을거리를 읽는다")을 직접 깎았다. → `reloadDocs()` 신설, `applyPull` 이 배치에 `docs` 행이 있으면 사본을 되맞춘다.
- **H2 · 연결 해제가 워터마크를 안 지워, 백엔드 리셋 시 조용한 분기.** `disconnectCloud` 가 자격증명 3키만 지우고 `watermark`·`cloud:pullMark` 를 남겼다. 다른 백엔드에 재연결하거나 D1 이 리셋되면(무료 티어 이빅션·마이그레이션 재생성) `collectOutbox` 의 `updated_at > 워터마크` 가 **기존 데이터 전량을 제외** → 새 서버가 내 데이터를 영영 못 받고 앱은 "연결됨·최신". v6 백필이 고친 유실과 같은 계열, 방향만 재연결 축. → 해제가 두 워터마크도 지운다(0 부터 재-push/pull 은 LWW 멱등이라 안전). 키를 `outbox.ts` 로 수렴해 `client↔run` 순환을 피했다.
- **H3 · 툼스톤 타이브레이크 비대칭 → 같은 ms 삭제↔편집이 영구 분기.** 부활 가드는 `deleted_at >= updatedAt`(동점 삭제 승)인데 툼스톤 DELETE 는 `updated_at < deletedAt`(동점 행 승)이라 방향이 엇갈렸다. A 가 삭제·B 가 같은 ms 편집하면 A=삭제·B=존재로 굳고 양쪽 "동기화 완료". → DELETE 를 `<=` 로 통일(**클라 `merge.ts` + 서버 `index.ts` 동시** — 한쪽만 고치면 기기별 병합이 갈린다). 서버 왕복 테스트가 실 workerd 로 검증.
- **H4 · flush↔merge 가 전역 `_last` 를 경합(잠재 유실).** `syncOnce` 재진입 가드는 sync-vs-sync 만 막는다. `applyPull` 의 `batchDb→readRows` 창에 useApp 디바운스 flush 가 끼어들면, 기준선이 안 세워진 사이 낡은 메모리를 더 큰 스탬프로 써서 받아온 행을 되돌릴 수 있었다(그 되돌림이 LWW 로 서버까지 이긴다). → `write.ts` 에 `runExclusive` 공용 primitive 를 두고 병합 쓰기를 flush 와 **같은 직렬화 체인**에 얹었다. 병합은 로컬 쓰기라 창 닫기 계약(§5-2 "로컬만 기다린다")을 안 어긴다.
- **H5(경미 5종)** — ① `Stamp` 상한(서기 2100): 거대 유한값이 `seedStamp` 래칫을 오염시켜 `nextStamp` 이 영원히 `_last+1` 만 내는 것 차단 · ② `graphData` 색 폴백을 배열 인덱스→`colorForId(id)`(절대규칙 #3, 0단계-G 가 폐기한 위치 기반 재발) · ③ 폰 SQLite 워커 사망 시 `_handle=null` 재생성 + 30s 호출 타임아웃(영구 대기 차단) · ④ 포커스 트랩이 숨은 요소(`offsetParent===null`) 제외 · ⑤ `useAiStream.run` 재진입 가드(겹침 continuation 이 새 실행 상태를 지우는 것까지) · ⑥ `syncSoon`(편집 디바운스)이 `beforeSync`(산출물 미러)·겹침 가드를 우회하던 것 수정.
- **게이트**: web verify(1028) · server verify(30 + 실 workerd 왕복 12) · build · budget · e2e 트랙 A(77) · **트랙 B 릴리스 exe(6)** · cargo(74) 전량 녹색. 동기화 코어 변경이라 dev 가 아니라 릴리스 exe 로 트랙 B 를 돌렸다.

## SD-6 데이터 폴더 격리 — 그리고 그 김에 드러난 부팅 결함 (2026-07-24)

- **셸이 SQLite 를 안 읽고 낡은 localStorage 로 부팅하고 있었다**(2단계-E 이후). `main.tsx` 는 _"`useApp` 은 `initAppStore()` 이후에 import 돼야 한다 — 모듈 평가 시점에 부팅값을 읽으므로 **순서가 계약**"_ 이라고 자기 주석에 못박아 두고, 바로 그 위에서 `ThemeProvider` 를 **정적 import** 했다. ThemeProvider → `useApp` 이고 ES import 는 호이스팅되므로, 스토어는 `initAppStore()` 가 시작하기도 전에 만들어졌다 → `preloadedState()` 가 null → localStorage 폴백. 2단계-E 가 `App` 만 동적 import 로 바꾸고 **형제 하나를 놓친** 형태다.
  - **교훈: 계약을 주석으로 적으면 그 파일 자신이 먼저 어긴다.** 같은 주석이 정확한 조건("useApp 을 끌어오는 정적 import 가 하나라도 있으면 안 된다")까지 적고 있었는데도 못 막았다. 이건 린트로 표현할 수 있는 종류다(main.tsx 의 정적 import 화이트리스트) — 지금은 하지 않았고 로드맵 항목으로 남긴다.
  - **왜 지금까지 안 드러났나 — 모른다.** 추정(C-5 부팅 pull 이 메모리를 덮어 가렸다)은 있지만 실측하지 않았다. **`initAppStore` 의 catch 가 완전히 무음**이라 진단 자체가 불가능했던 것이 이 결함의 수명을 늘렸다(형제인 `getDb()` 는 같은 이유로 이미 로그를 남기고 있었다 — 여기만 빠져 있었다). → 로그 추가.
  - 잡은 것은 **트랙 B 의 재시작 케이스**다. 정적 검사·유닛·트랙 A 는 원리적으로 못 본다(스토어 생성 순서는 번들 평가 순서의 함수라 진짜 앱을 껐다 켜야 관측된다). 이 저장소가 다섯 번째로 "전량 녹색인데 실물에서 죽는" 부류를 만났고, 이번엔 **그 층이 있어서** 사용자 앞이 아니라 게이트에서 드러났다.
- **격리 자체** — `LEARNING_HUB_E2E_DATA_DIR` 이 있으면 DB·`workspace.json`·`research-jobs.json`(원래 한 폴더인 삼형제)이 함께 옮겨간다. `src-tauri/src/paths.rs` 가 그 해석의 단일 원천.
  - ⚠ **`APPDATA` 를 갈아끼우는 방식은 안 통한다**(실측): `dirs-6.0.0/src/win.rs:10` 이 Win32 `SHGetKnownFolderPath` 를 부른다. 그래서 우회가 아니라 **앱이 스스로 읽는 override** 여야 했다.
  - 지렛대는 `tauri-plugin-sql` 의 `path_mapper` 가 `PathBuf::push` 라는 점 — 인자가 절대경로면 앞을 통째로 버린다(`wrapper.rs:319`). 그래서 override 시엔 완전한 경로를 준다.
  - **값을 두 벌 두지 않는다**가 이 변경의 핵심 안전 요구다. 프런트가 연결 문자열을 상수로 따로 들면 백엔드는 A 에 마이그레이션하고 프런트는 B 를 여는 상태가 되고, 그 증상은 **"데이터가 없다"는 조용한 화면**이다 → `db_url_cmd` 커맨드 하나로 수렴.
  - 환경변수가 없으면 코드 경로가 **이전과 한 글자도 다르지 않다**. 위험이 비대칭이라(모든 사용자 데이터의 경로 해석) opt-in 을 설계에 넣었다.
  - 부수 효과: 하네스의 **원복 로직이 사라졌다**(로드맵이 예고한 그대로). 검증이 검증 대상을 되돌려 놓아야 하는 구조 자체가 없어졌다.

## C-6 직전 감사 — LAN 서버 은퇴 · 폐기 경로 신설 · 왕복 테스트 층 (2026-07-20)

- **`server.rs`(LAN 모바일 뷰 서버, 845줄) 은퇴** — 설계서 §9-1 이 _"C-4 전에 정해야 한다"_ 고 못박았는데 C-4·C-5 를 둘 다 넘기고서야 정했다(사용자 결정). 남길 유일한 논거였던 "인터넷 없을 때 집 안 폴백"이 **C-6 폰의 로컬 캐시로 이미 덮인다**는 것이 판정 근거다. 반대로 남기면 폰 번들이 **백엔드 둘·인증 두 벌**을 상대하는데, LAN 쪽은 `server.rs:330` 이 **만료 없는 PSK 를 URL 에 싣는** 방식이라 §6 P0-2 가 명시적으로 금지한 형태다 — 금지한 모델과 권장 모델이 한 저장소에 공존하면 다음 사람이 가까운 쪽을 베낀다. 부수 효과로 4단계-G 의 **"앱이 여는 포트가 0"** 이 복원됐다. `rows.rs`(§9-3b 이후 영구 사장)도 함께 삭제 — _"'있었다'가 '옮겨야 한다'는 아니다"_.
- **기기 폐기(revoke) 경로 신설** — C-4 는 `revoked_at` 열을 만들고 `/api/token` 이 **읽게** 해 뒀는데 **그 값을 쓰는 코드가 없었다.** 폐기가 스키마와 검사만 있고 실행 경로가 0 이라, 폰 분실 시 대응이 "D1 에 손으로 SQL"뿐이었다(문서·런북은 구현된 기능처럼 서술). 인증을 **관리 비밀이 아니라 액세스 토큰**으로 한 이유: 폐기가 필요한 순간에 사용자가 쥔 것은 남은 기기이지 어딘가에 보관한 비밀이 아니다. 도난 기기가 PC 를 끊을 수 있다는 대가는 **의도적으로 수용**했다 — 그 기기는 이미 데이터 전량을 읽고 쓸 수 있어 권한 상승이 아니라 불편이고, 폐기를 어렵게 만드는 쪽이 실제 위협에 대한 대응 수단을 없앤다.
- **리프레시 회전은 하지 않는다** — 설계서 P0-2 가 "수명·회전·폐기"를 함께 적었지만 회전만 뺐다. 이득은 탈취 *탐지*인데 대가는 **응답 유실 시 영구 잠금**(서버는 회전했는데 클라이언트가 새 토큰을 못 받으면 그 기기는 죽는다)이고, 유예 창으로 완화하면 탐지력이 그만큼 준다. 사용자 1명·기기 2대·192비트 난수·현실 유출 시나리오가 "기기 분실"뿐인 이 앱에서는 **짧은 액세스 수명(15분) + 폐기**가 실효 대응을 이미 준다. **문서를 코드에 맞췄다** — 넣지 않은 것을 넣었다고 적어 두는 편이 훨씬 위험하다.
- **`capBatch` 를 `outbox.ts` → `contract.ts` 로 이동** — 순수 함수인데 **IO 모듈에 갇혀 서버가 import 할 수 없었고**, 그래서 pull 이 같은 자르기 규칙(스탬프 그룹 불가분)을 손으로 다시 쓸 뻔했다. 이 저장소가 `rows.ts`↔`rows.rs` 로 두 번 물린 divergence 를 세 번째로 사기 직전이었다. 이제 **push 와 pull 이 같은 함수를 쓴다.**
- **실 workerd 왕복 테스트 층 신설**(`server/test/roundtrip.test.ts`) — 이 감사의 가장 값나가는 산출물. 기존 검사망은 이 부류를 **원리적으로** 못 잡는다(유닛은 전송을 목으로, 트랙 A 는 CSP 없는 Chromium, 트랙 B 는 클라우드 경로 미주행). 그래서 사고 **네 번**이 전부 _전량 녹색인 상태에서_ 났다 — 2단계 저장 · C-4 삭제부활 · C-5 CSP · pull 페이지네이션. 그때마다 문서는 _"띄워보지 않으면 모른다"_ 고 적었지만 **그 층은 만들지 않았다.** 교훈을 문장으로 저장하면 반복되고, **하네스로 저장해야 멈춘다.** 12케이스 1.7초. 함께 `server/` 를 CI 에 편입했다 — 인터넷에 노출되고 인증을 다루는 층인데 **워크플로 `paths` 에도 잡에도 없었다.**
- **`.prettierrc.json`·`.gitattributes` 를 루트로 승격** — 둘 다 `web/` 에만 있어서 나중에 생긴 `server/` 가 **어느 쪽에도 안 걸렸다**(새 클론에서 CRLF → format:check 파손). 폴더가 늘 때마다 규칙을 복사하는 대신 루트에서 한 번 못박는다.
- **체크섬 핀의 면제 구간을 없앴다** — `if (!pinned) continue` 가 v5·v6 을 무방비로 통과시켰고, 그 둘은 이미 실 DB 에 적용돼 sqlx 불변인데 CI 가드가 없었다. "아직 배포 전이라 예외"가 왜 틀렸나: 마이그레이션이 실 DB 에 적용되는 시점은 **배포가 아니라 개발자가 앱을 한 번 띄우는 순간**이라 면제 구간이 실질적으로 존재하지 않는다. 이제 **핀 없는 버전은 테스트 실패**다.

## 계획 탭 v6 (2026-07-18 · 평가 60% 후속 보강 + 6차 피드백)

- **일정(`events`) 개념 신설** — 과목에 묶인 공부 블록도, 요일 반복 일과도, 체크해서 끝내는 할 일도 아닌 **단발 약속·시험**을 담는 축이 없었다. `tasks` 확장이 아니라 독립 타입(`PlanEvent`)을 택한 이유: '할 일'(완료 개념 있음)과 '일정'(그 시각에 일어남)은 의미가 다르다. 시각이 필수라 종일 행으로 새지 않는다.
- **일정은 가용시간을 깎는다** — 사용자 선택. 3시에 2시간 약속이 있으면 공부 가용이 줄고 자동초안이 그 자리를 피해야 계획이 현실과 맞는다. **이중 차감을 구조적으로 차단**: 차감분을 `freeWindowsForDay`(요일 창 − 일정 구간)의 창 총합 델타에서 **유도**한다 → 수업과 겹친 일정은 0분, 수면 중 일정도 0분, 겹친 두 일정은 합집합만 1회. `dayOverrides`(명시 오버라이드) 위에서도 깎는다 — 오버라이드는 '공부 가능 시간'의 선언이고 약속은 그와 직교하기 때문.
- **일정 색 = `--event` 전역 토큰** — PALETTE(초록–민트–시안)는 과목이, 세션 다섯은 `--acc/--acc2/--warn/--violet/--bad`가 이미 물어 남은 의미론 대역이 violet↔bad 사이 마젠타뿐이었다. 처음엔 주/월과 일 뷰가 각자 색을 유도해 **같은 일정이 뷰마다 다른 색**이 됐다 → `tokens.css`의 단일 토큰으로 승격. 두 유도원(`--violet`·`--bad`)이 테마마다 뒤집히므로 `data-theme` 분기 없이 양 테마 성립.
- **배분 보드는 행을 늘리지 않는다(되돌림)** — 감사가 "보드 아래 175px 빈 공간"을 지적해 행을 `minmax(48px,1fr)`로 신축시켰다가 **사용자가 거부**("과목마다 일정 크기 블록이었는데 왜 꽉 차게? 추가하면 나눠지는 건 이상하다"). 사용자가 옳다 — 매트릭스의 행은 **이산 항목**이라 늘리면 빈 셀만 커진다. 캘린더의 시간축(연속량)과 반대다. 고정 행 높이로 복원, 아래는 여백으로 둔다.
- **일 뷰 빈 상태는 화면을 덮지 않는다(되돌림)** — EmptyState 조건을 넓혀 5분기 진단으로 레이아웃을 대체했다가 거부됨("원래처럼 왼쪽 블럭·오른쪽 일일 시간이면 된다"). 좌 트레이/우 타임라인은 **항상** 띄우고, 원인은 트레이 안 한 줄 힌트 3분기로 축소.
- **타임라인 범위 = 깨어있는 창 전체** — 옛 '일정 있는 구간 ±1h'는 빈 날 폴백이 `wake0+8h`라 **07:00–15:00만** 그리는 버그를 냈다. 창 밖 일정은 union해 잘림 방지.
- **시간당 높이는 프레임에서 역산하되 하한 44px** — 주간이 심야를 접고도 트랙이 화면보다 짧아 아래가 비었다("남은 시간이 시간당 간격이 커지면서 꽉 차야"). 남는 높이를 시간 행이 나눠 갖되 **44px 밑으론 안 눌린다** — v5가 비율 배치를 걷어낸 이유(30분짜리가 뭉개짐)를 보존. 넘치면 스크롤.

## 계획 개편 — 일일 배치 레이어 + 계획 1탭 통합 (2026-07-18)

> 트리거: "계획표 짜는 탭들(주간 스케줄·학습 항목·연동)을 대대적 개편 — 일일 계획을 디테일하게, 굳이 따로 있을 필요 없다." 상세 설계 = `docs/계획개편-설계.md`(SSOT).

- **배치 기본 뷰 = 일(day)** — "오늘 계획 짜기"(Today CTA §7) 진입이 곧 오늘 편집기. 구 `SchedView`(overview/cards)는 `week`로 흡수(preprocess+`.catch('day')`, 부분손상 격리). 카드뷰는 위크보드와 정보 중복이라 제거.
- **복습 재씨앗은 guarded 후처리(§4-3)** — `reseedManualReviews`가 `applyDayPlans` 직후 수동 날의 `new` 블록 하류 복습을 보강하되, **manual 날 없으면 무동작**(자동 불변)이고 대상 날에 이미 그 챕터 rev가 있으면 skip(이중계상 방지). 인라인 자동 씨앗 경로는 불변 — 회귀 위험 격리.
- **볼트 불러오기는 코드 이동 아닌 lib 공유** — 레이어 경계상 feature→feature import 금지라, 과목 세그먼트는 `items/VaultImport`가 연동 탭 `VaultPanel`과 **같은 `lib/vault` 함수·같은 쿼리 캐시(['vault'])**를 호출(두 곳에서 같은 훅). 해제/트리 상세는 연동 탭 소유.

## 계획 UX 폴리시 + 블록 모델 (2026-07-18)

> 트리거(3차 피드백): "배분 보드 UX/UI가 조잡·접근성·조망성 부족" + "+블록이 같은 과목이면 하나로 누적된다 — 별도 블록이어야, 블록 길이도 바꿀 수 있어야."

- **배분 보드 = 값의 시각적 무게로 읽는다** — 셀에 배분 분량 비례 과목색 채움(`fillAlpha` 0.16~0.5)으로 주(週) 부하를 한눈에. 균일 회색 스프레드시트(숫자 나열)는 "한눈 조망" 목표에 반한다.
- **드래그 배분은 순수 편의 레이어, 접근성 정본은 숫자 입력** — 과목 행을 요일 칸에 드롭하면 +1h. 셀은 `<input type=number step=0.5>`라 ↑↓·타이핑이 이미 WCAG 2.1.1 대안 → 드래그에 별도 키보드 대안 불필요(드래그는 마우스 편의만 얹음). 드롭은 잡은 과목 행에만 허용(과목→요일 의미 유지).
- **모바일 = 스티키 좌우 열(설계의 아코디언 대신)** — 좌(과목명)·우(예산상태) 열 + 헤더 행을 `position:sticky`로 고정, 요일만 가운데서 스크롤. 설계 §12-6의 "과목 아코디언"과 **같은 목표**(가로 스크롤에도 라벨·상태 유지)를 훨씬 저위험으로 달성. 함정: `.grid overflow:hidden`이 sticky 컨테이닝 블록을 가로채므로 제거하고 네 모서리 셀 라운딩으로 대체.
- **리드아웃 = 배분과 직접 관계된 숫자만** — 오해 소지 '가용 113h'(주당 수십h 총량) 제거, **배분/주당예산 · 달성%**로. 툴바 중복 배분합도 제거(상단 크롬이 소유).
- **+블록 = 별도 블록(병합 제거) + 블록별 완료** — 같은 sid|type 누적 병합(`addOrMergeBlock`)을 `addBlock`(독립 블록)으로. 충돌(완료키가 `sid|type` 그날 단위라 한 체크가 둘 다 토글)은 **블록별 `done` + 집계 미러링**으로 해소: `setBlockDone`이 `block.done`을 세팅하고 `completions[ds][sid|type]`를 그날 done 블록들의 **OR/합**으로 재계산. 하류(스케줄러 복습씨앗 `pushReviewTasks`·통계·.ics는 이 집계만 읽음)는 **무변경**. 대안(완료키에 blockId 추가)은 하류 전면 개편이라 기각. 승격 시 기존 `sid|type` 완료를 블록 `done`으로 시딩(체크 유실 방지 · 승격 시엔 키당 1블록이라 무모호).
- **블록 길이 인라인 편집 = 스테퍼 버튼** — 트레이 블록/할일에 −/＋ 30분 스테퍼. `<input>`은 `draggable` 행과 텍스트 선택·드래그가 충돌해 버튼으로(타임라인 카드는 기존 리사이즈/편집바 유지).
- **efficacy 안내** — 계획상 챕터를 다 배우게 된 과목(`itemStat.finished`)에 배분해도 `new` 블록은 안 생기고 복습·Anki만 얹힌다(엔진의 챕터 소진 판정). "배분했는데 왜 안 굴러가나"를 보드 노트로 명시(엔진 시맨틱은 규칙 #4로 불변 — 안내만).

## 계획 재개편 v3 — 뼈대·과목 병합, 상세는 시트로 (2026-07-18)

> 트리거(4차 피드백): "과목하고 뼈대 탭을 합치면 좋겠다 — 과목 탭 유형으로 가되 층을 나눠 위=뼈대·아래=과목/볼트, 오른쪽에 가용시간. 배분도 흡수. 과목 누르면 아래로 펼쳐지는 게 아니라 탭 프레임보다 작은 새 페이지가 떠서 그 과목 배분까지."

- **계획 3세그먼트 → 2세그먼트(과목·배치)** — 뼈대(가용시간·수업·일과)와 과목은 둘 다 "정의"(가끔 정하는 것)이고 배치는 "운영"(매일 보는 것)이다. 리듬이 같은 둘을 한 층위에, 다른 하나를 옆에 두는 게 맞다. `SUBTAB_GROUPS=['plan-host','items','schedule']`.
- **병합 = 폴더 물리 이주(경계 규칙의 강제)** — `eslint-plugin-boundaries`가 `features → features` import를 error로 막으므로 화면만 합칠 수 없다. `routine/{Routine,DayRing}` → `items/{SkeletonPanel,DayRing,AvailRail}`로 이동. `routine` 키는 **리다이렉트 shim**만 남겨 `g o`·⌘K·기존 `/routine` 딥링크와 invariants(TABS↔LOADERS 패리티)를 지킨다.
- **배분은 '흡수'가 아니라 '미러'** — 사용자 원안은 배분 보드를 과목 탭에 흡수였으나, 보드의 핵심 가치는 셀 편집이 아니라 **열 합계(요일별 배분/가용 초과)** 라는 교차 조망이다. 과목 상세는 매트릭스의 **한 행**만 보여줄 수 있어 "화요일이 이미 초과인지"를 못 보여준다 — 재개편 v2가 세운 '배분 보드=계획의 중심'과 정면 충돌. 그래서 **보드는 배치에 그대로 두고**, 상세 시트와 우측 레일이 같은 `lib/weekAlloc`(allocView/setAllocCell/colSumMin)을 호출한다. **두 입구, 한 진실**(별도 상태 없음 → 자동 동기).
- **아코디언 → 중앙 시트** — `ItemCard` 제자리 펼침은 뒤 카드를 밀어 갤러리 조망을 깨뜨렸다(과목이 늘수록 악화). `SubjectSheet`가 뒤 갤러리를 그대로 둔 채 한 과목만 판다. 카드는 '읽는' 물건, 편집은 전부 시트가 소유. 시트 안에서 **정의(주당 목표·챕터·마감)와 배분(요일 7칸)을 함께** 정한다 — 예산과 분배가 갈라져 왕복하던 문제 해소.
- **`DetailDrawer`에 `placement='center'` + body 포털** — 셸 조상이 스태킹 컨텍스트를 만들어, 포털 없이는 `position:fixed`가 뷰포트가 아닌 그 조상 박스 기준으로 잡히고 z-index도 갇힌다(헤더·사이드바가 오버레이를 덮고 패널 헤드가 잘림). 중앙 시트를 만들며 드러난 **기존 우측 드로어의 잠재 결함**이라 컴포넌트 차원에서 고쳤다.
- **뼈대도 같은 중앙 시트(제자리 펼침 아님)** — 처음엔 요약 스트립 + 인라인 펼침으로 짰으나, 그건 `ItemCard` 아코디언을 걷어낸 이유(뒤 콘텐츠가 밀려 조망이 깨짐)를 그대로 반복하는 것이었다. **한 탭 안에서 '펼침'과 '시트' 두 어휘를 섞지 않는다** — 요약 바는 상시(가용·수업·일과), 편집기는 과목과 동일한 `DetailDrawer placement='center'`로. 시트 안에서 수업·일과 카드는 2열.
- **reduced-motion 백스톱에 delay 0 추가(기존 결함)** — 전역 백스톱이 `animation-duration`만 0.01ms로 죽이고 `animation-delay`는 남겨둬, `ds.card`의 스태거(nth-child 0.05~0.24s)가 `fill-mode:both` 탓에 지연 구간 내내 `opacity:0`에 머물렀다. 모션 자제 사용자에게 카드가 최대 240ms 비는 건 '즉시'가 아니다 → `animation-delay/transition-delay: 0s !important`. `data-fx='lite'`도 동형. (시트 스냅샷이 두 번째 카드를 투명하게 박으면서 드러난 **선재 결함** — 병합 작업이 만든 게 아니다.)
- **시각 스냅샷은 뷰포트 캡처 + 불투명 대기** — 시트는 `position:fixed`라 `fullPage`가 스크롤 오프셋만큼 어긋나게 그린다(헤더 누락·좌측 잘림). 또 `toBeVisible`은 opacity를 보지 않아 진입 애니 첫 프레임을 박을 수 있어, 카드 `opacity:1`을 명시적으로 기다린 뒤 찍는다.
- **요일 막대 = 용량 위 적재** — 우측 레일 막대의 중립 틀=그 요일 가용, 안쪽 액센트 채움=이번 주 배분(초과면 `--bad`). 보드의 열 맥락을 과목 탭에 **최소한으로** 이식한 것 — 시트에서 칸을 채울 때 "그 요일이 찼는지"를 레일에서 읽으라는 뜻.

## 계획 재개편 v4 — 캘린더 독립·배분 승격, 캘린더 재작성 (2026-07-18)

> 트리거(5차 피드백): "캘린더뷰(일·주·월)가 가장 앞, 그다음 배분을 독립탭으로, 그다음 과목 순. 그리고 캘린더 뷰 아직 너무 조잡하다 — TickTick을 보고 디테일하게."

- **계획 세그먼트 = [캘린더 · 배분 · 과목]** — 배분은 주(週) 단위로 한 번 정하는 '전략', 캘린더는 매일 보는 '전술'이라 리듬이 다르다. 뷰 스위치(`schedView`) 안에 섞여 있으면 계획의 축이 흐려져 `alloc`을 독립 탭으로 승격했다. `schedule`은 '배치'→'캘린더'로 개명하고 [일·주·월]만 소유. 기본 착지도 배분→캘린더 주 뷰로(`defaultUI().schedView='week'`).

- **탭 경계를 넘는 드릴다운은 URL이 통로, 뷰 전환은 보내는 쪽이** — 배분 보드의 셀/요일 클릭 → 캘린더 일 뷰. 한 컴포넌트 안일 땐 `setAnchorDs+setView`로 끝났지만 이제 탭이 갈렸다. 받는 쪽 effect에서 `setState`로 되받는 건 캐스케이드 렌더라 린트가 막는다(`react-hooks/set-state-in-effect`) → **보내는 쪽이 `setSchedView('day')` 후 `/schedule?ds=`로 이동**하고, 받는 쪽은 `?ds=`를 `useState` 초기값으로만 읽는다.
- **주 캘린더 전면 재작성 — 비율 배치 → 고정 픽셀 격자** — 옛 구현은 하루를 열 높이 100%에 매핑하고 3시간 격자를 그렸다. 그 결과 30분 세션이 몇 px로 뭉개져 이름조차 안 보였다(사용자가 "조잡"이라 부른 실체). **1시간=48px 스크롤 격자**로 바꾸고 30분 보조선·현재 시각 라인+배지·마운트 시 '지금'으로 자동 스크롤을 얹었다.
- **겹침은 `packLanes`(순수 함수 · lib)** — 겹치는 일정을 나란한 레인으로. 폭 분모는 **그 클러스터의 레인 수**다(전역 최대가 아니라) — 하루 한 번 3중 겹침이 났다고 나머지가 다 1/3로 쪼그라들면 안 된다. DOM·픽셀 무관이라 `test/packLanes.test.ts` 8케이스로 잠갔다.
- **시각 없는 것은 시간축에 두지 않는다** — 마감·미배치 학습을 상단 **종일 행**으로 분리(옛 구현은 시간축 안에 배지로 섞여 있었다).
- **월 뷰: 히트맵 → 일정 칩 격자** — 히트맵은 "얼마나 했나"만 답했고 **그날 뭘 하는지**를 못 보여줬다. 칸마다 과목 색점+이름 칩 + "+N개 더". 히트맵의 가치(달 부하 리듬)는 버리지 않고 칸 배경 옅은 틴트로 계승 — **칩은 '무엇', 틴트는 '얼마나'**.
  - 칩 정렬은 `new > mock > blank > rev > anki`. 매일 도는 Anki가 매 칸 첫 줄을 차지하면 달 전체가 같은 모양이 돼 아무것도 안 읽힌다.

  - 칸 최소 높이 76px + 부족하면 세로 스크롤. 6주를 720px 창에 1fr로 나누면 칸이 54px가 돼 둘째 칩이 반쯤 잘렸다 — **잘린 칩은 정보가 아니라 노이즈**(읽히지도, 없지도 않음).
- **월 네비는 공통 nav가 소유** — 뷰 본문이 자체 헤더를 또 그리면 헤더가 두 줄이 되고 정작 nav 줄은 뷰 스위치만 남아 빈 띠가 된다. 주 뷰의 주 이동과 같은 자리·같은 문법으로 통일.
- **`scrollTo` 대신 `scrollTop` 대입** — 초기 스크롤 위치엔 애니메이션이 불필요하고, jsdom엔 `Element.scrollTo`가 없어 테스트에서 컴포넌트가 통째로 터진다(실제로 그렇게 깨졌다).

## 캘린더 v5 — 바탕을 비우고 블록만 세운다 (2026-07-18)

> 트리거(6차 피드백): "왜 일·주·월 다 칸에 기본 색을 깔아놨나 — 더 안 보인다. 하얀 바탕에 블록만 강조하는 다른 웹들처럼, 우리는 검정이니 검정에서 강조되는 색으로." + 정렬·범위·클릭 영역·삭제창 결함 다수.
> ⚠️ v4에서 'TickTick 규약'이라 적은 근거는 **실제로 확인하지 않은 것**이었다. 이 항목이 정정한다.

- **바탕 틴트 전면 제거(세 뷰 공통)** — 주=오늘/선택 열 액센트 틴트, 월=부하 히트맵 틴트, 일=가용창 초록 밴드. **바탕이 물들면 그 위 블록의 대비가 깎여 정작 강조할 것이 안 보인다.** 오늘 표시는 머리글 날짜 알약 + 현재 시각 라인으로 충분하고, 가용창은 채움 없이 점선 윤곽만 남긴다(빈 시간은 '비어 보여야' 한다). 월 뷰 주말도 바탕 대신 날짜 숫자 색만 낮춘다.
- **블록은 검정 위에서 또렷하게** — 채움 16%→34%(#0b0d12 기준), 좌측 색 띠 3→4px, 안쪽 테두리 55%, 글자 흰색. 색은 여전히 과목색(`--seg`) 파생이라 전 탭 어휘는 유지.

  - 이관을 가능케 한 것은 **`AppHandle` 을 로직에서 걷어낸 것**(규율 11-2). `vault::scan_at` · `research::restored_from` · `vault::watch_with` 를 새로 갈랐고, `server::start_with` · `artifact::read_at` · `anki_scan::scan_at` 은 이미 그 형태였다. 커맨드가 핸들을 로직에 섞으면 **검사가 자동으로 GUI 층으로 밀려 올라간다** — 이게 이 사고의 구조적 원인이다.
  - **조용한 skip 을 만들지 않는다**: 리소스 부재로 그냥 통과시키면 "녹색인데 아무것도 안 쟀다"가 되어 같은 병을 재발시킨다. 환경 가정은 `testkit` 의 단일 테스트가 시끄럽게 단언한다.
- **⚠ 검증이 사용자 데이터를 망가뜨리고 있었다(이 작업 중 실측 발견).** 트랙 B `4단계-J` 가 실물 DB 에 `INSERT OR REPLACE INTO docs (key, value)` — **2열**로 썼다(뒷정리도 동일). `updated_at` 이 `DEFAULT 0` 이 되고, 아웃박스는 `updated_at > watermark` 로 수집하므로 **사용자의 독후감(`lh:reads`)이 클라우드로 영원히 안 올라가는 상태**였다. 앱은 그동안 "연결됨 · 최신 상태"라고 말한다.
  - 앱의 쓰기 경로(`lib/db/docs.ts:51`)는 3열로 **정상**이다 — 망가뜨린 것은 검증 하네스다.
  - 옆 케이스(C-5 `updated_at=0` 검사)가 그걸 결함으로 잡고 있었다. **테스트가 원인이자 검출자**였고, 케이스 순서/뒷정리에 따라 통과했다 실패했다 한다.
  - **v6 백필로는 안 고쳐진다**: `006` 은 0 스탬프를 **상수 1** 로 올리는데, 이미 한 번이라도 동기화한 기기에선 `1 > watermark` 가 거짓이라 그 행은 여전히 안 올라간다. 워터마크보다 큰 값이 필요하다(`examples/repair_stamp.rs` 로 1행 복구 완료). **이건 v6 설계에 남아 있는 잠재 결함이다** — 같은 상황의 다른 기기가 생기면 다시 물린다.
  - → 규약: **트랙 B 는 사용자 실물 DB 에 쓰지 않는다.** 쓰기 계약을 검사해야 하면 임시 DB 로 `cargo test` 에서.
- **덤으로 잡은 잠재 flaky — 부팅 하이드레이션 경합.** 남은 트랙 B 케이스를 다듬다 두 번 물렸고, 둘 다 **앱이 아니라 테스트 결함**이었다. 원인 하나다: SQLite 부팅 읽기가 **비동기**라, 그 전에는 `ThemeProvider:14` 의 `theme || 'dark'` 가 **기본값을 먼저 내리고** `toggleTheme`(`actions.ts:264`)도 `st().state.theme || 'dark'` 로 **기본값에서** 다음 값을 계산한다.
  - 증상 ①: 부팅 직후 `data-theme` 을 저장값과 비교 → 기본값을 재서 틀린 실패.
  - 증상 ②: 부팅 직후 토글 클릭 → 저장값이 이미 그 결과와 같으면 **아무 변화가 없고** "flush 가 안 됐다"로 잘못 실패.
  - ②는 **원본 케이스에도 있던 잠재 flaky** 다 — 저장값이 `dark` 일 때만 우연히 통과했다. 통과하던 테스트를 옮기면서 드러났다.
  - 처방: 클릭·비교 전에 **화면이 저장값으로 수렴하기를 폴링**한다. 기본값과 저장값이 다르면 진짜로 기다리고, 같으면 어느 쪽에서 계산해도 결과가 같아 즉시 통과해도 안전하다. 부수 효과로 "부팅 읽기가 화면까지 도달한다"까지 함께 잠긴다.
  - 일반화: **비동기 하이드레이션 위에서 `waitForTimeout` 으로 버티지 말 것.** 관측 가능한 수렴 조건으로 바꾸면 느려지지도 흔들리지도 않는다.
- **작업 중 확인은 `tauri:dev` 상시 유지**(재기동 0 · HMR). 단 dev 는 `devCsp`(느슨)에 오리진이 `localhost:5173` 이라 **CSP·오리진 결함이 안 나타난다**(C-5 가 그 부류) → 완료 선언 전엔 릴리스 exe 로 트랙 B 1회. 그 1회도 `tauri:build:fast`(`--no-bundle`)면 NSIS 단계가 빠진다.
- **결과**: 트랙 B 16 → 5, 회당 앱 기동 19 → **2**, 실행 **~21초**(연속 실행 동일 — 결정적). 2번의 내역: 공유 셸 1(앞의 네 케이스 + 닫기 케이스의 편집·닫기까지) + 원복용 재기동 1.
  - **왜 1번이 안 되는가**: 닫은 뒤의 *값 확인*은 Node 가 SQLite 를 직접 읽으면 되지만(`node:sqlite`, Node 24 내장), **원복**은 앱 자신의 쓰기 경로로 해야 한다 — 하네스가 실물 DB 에 직접 쓰는 순간이 정확히 위의 `updated_at` 유실 사고다. 8초를 아끼려고 그 문을 다시 열지 않는다.
  - **⚠ 진짜 남은 문제는 기동 횟수가 아니라 "E2E 가 사용자의 실 데이터를 상대한다"는 것이다.** 그게 위 데이터 손상 사고의 근본 원인이고, 원복 로직·`_test` 흔적 정리 같은 잡동사니도 전부 거기서 나온다. 폐기 가능한 데이터 폴더로 띄울 수 있으면 **기동 횟수가 아무래도 상관없어진다**(복원 불필요·손상 위험 0).
    - 환경변수로는 안 된다 — **실측(소스)**: `dirs-6.0.0/src/win.rs:10` → `known_folder_roaming_app_data()` → `SHGetKnownFolderPath(FOLDERID_RoamingAppData)`. `dirs-sys` 의 `env::var` 는 Unix 의 HOME/XDG 에만 쓰인다. 즉 `APPDATA` 를 갈아끼워도 앱은 실제 폴더를 본다.
    - → 앱 쪽에 데이터 폴더 override 가 필요하다(`db.rs` 의 `DB_URL` 과 프런트의 db 식별자가 함께 움직여야 한다). **이번 작업에 넣지 않았다**: 모든 사용자 데이터가 걸린 경로 해석을 검사 편의로 건드리는 건 위험이 비대칭이다. 별건으로 로드맵에. `cargo test` 93개가 ~4초. 커버리지는 줄지 않았다 — 오히려 Rust 층에서 케이스를 더 촘촘히 넣었다(볼트 감시 필터·복원 전이·WAL 동시 쓰기 등 옛 트랙 B 가 안 보던 것들).
